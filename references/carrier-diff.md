# 同一人设在不同载体上的改写方法

适用场景：同一个人设要同时落到大屏数字人、具身机器人本体、AGV 移动底盘、自助设备大屏、线上智能体、IM 机器人、电话外呼等不同载体上时，用来判断哪些内容必须改、哪些可以留、每个载体各自的硬约束是什么。也用于处理「同一人设换载体后突然开始承诺做不到的事」「动作括号被念出来」「字数限制一刀切失效」这类问题。

---

## 一、先建载体清单，再动笔改人设

不要先写 Prompt 再想载体。先填这张清单，每一项都写死，写不出来就说明这个载体还不能配。

| 载体 | 素材中的实例 | 硬约束（不可改） | 人设可动范围 |
|---|---|---|---|
| 大屏数字人 | 某能源企业展馆「小智」、展厅「知夏」、某石窟景区贩卖机「龙小灵」 | 屏幕不可移动；无物理带路能力；无身体动作 | 语气、岗位、字数、状态机 |
| 具身机器人本体 | 某能源企业展馆「沪小能／小电」、某科技公司「小白／小智」、宇树 G1、西岸美术馆「西小岸」 | 动作由硬件中控执行；大模型只拿到文本；部分机型无视觉感知 | 语气、口头禅、自嘲点、字数额度 |
| AGV 移动底盘 | 某科技公司总部「小派」 | 地图词条是白名单，未入库地点无法到达；底盘动作由中控驱动 | 追问逻辑、话术格式、迎宾语 |
| 自助贩卖机大屏 | 某石窟景区「龙小灵」 | 站立停留时间极短；价格以机身标价为准，不可口头承诺 | 导览与带货的配比、语气 |
| 线上智能体 / App | 素材未覆盖 | 素材未覆盖 | 素材未覆盖 |
| 飞书 / IM 机器人 | 素材未覆盖 | 素材未覆盖 | 素材未覆盖 |
| 电话外呼 | 素材未覆盖 | 素材未覆盖 | 素材未覆盖 |

判断分支：

1. 载体有身体（机器人本体、AGV）→ 必须处理「动作归谁」问题，见第六节。
2. 载体有屏幕但不可移动（大屏、贩卖机）→ 必须处理「做不到的事怎么回」，见第九节。
3. 载体无身体且无屏幕（线上、IM、电话）→ 素材未覆盖，不要套用线下载体的字数与触发逻辑，重新判断。

只写素材里有依据的载体。线上智能体、IM 机器人、电话外呼这三类在本次素材中没有可引用的 Prompt 样本，不要从线下载体类比推导。

## 二、逐载体的硬约束与改写动作

### 2.1 大屏数字人：把「不可移动」写成能力边界

改写动作：删掉所有需要位移、带路、指路的表述，改为「口述路线 + 引流到能动的那台设备」。

用户原话（第 182 轮）：

> 我现在想调整几个地方：1、因为大屏是没办法移动的，所以当前台场景出现问她会议室怎么走的时候他是没办法带路的，我会把她当前的屏幕位置到各个会议室的行走路线描述补充在知识库内。然后他依据知识库内容回复路线，同时补充：我们的展厅还有AG小车、轮式机器人，如需带路可以移步体验区哦。

落地写法（原文）：

```markdown
**规则 1：前台路线指引与多设备联动**: 当在前台场景中，用户询问"会议室怎么走"或某个区域路线时，你【必须严格依据知识库】告知从当前大屏出发的行走路线，并且在回答的最后【必须一字不差地补充这句话】："我们的展厅还有AG小车、轮式机器人，如需带路可以移步体验区哦。"
```

判断分支：

- 路线知识库里有 → 按知识库口述，末尾补联动话术。
- 路线知识库里没有 → 不猜路线，直接走引流话术，并建议联系现场工作人员。
- 不要写「我带你过去」「请跟我来」。大屏没有这个能力，写进 Prompt 就是让模型现场翻车。

### 2.2 具身机器人本体：把「感知」和「台词」彻底分开

改写动作一：先确认这台机器人在大模型侧能看到什么。看不到的，一律不能当触发条件。

用户原话（第 78 轮）：

> 我觉得这个限制有问题，触发条件也有问题，他没有视觉感知，不知道什么是A区，也不知道什么是移步指导，而且不是所有人都是王总，他要能根据第一个指令告诉他的人名进行介绍才对。触发条件应该是文本指令触发

改写后的触发写法（原文）：

```markdown
**阶段三：移步引导（准备去B区）**
*   **触发文本暗号**: 引导员发送包含【"视频看完了"】、【"去下一个展区"】或【"继续接待任务"】的句子。
*   **你的唯一回复**: "好的，`[称谓]`，各位领导，请跟我一起去见我的另一个小伙伴。"
```

改写动作二：人名不写死，改成变量抓取 + 兜底。

```markdown
# 核心机制：动态人名抓取与锁定
**人名锁定法则**: 在引导员（用户）向你发出第二轮指令时，他会介绍来访的领导（例如："向王总/张董/李部长简单介绍一下"）。你【必须】敏锐抓取这个称谓（如：**王总**、**张董**、**李部长**），并将其存入你的多轮记忆中。在后续的所有回答中，你【必须】将"王总"替换为该称谓。如果未抓取到具体姓氏，默认使用"各位领导"。
```

判断分支：

- 客户能保证每场都是同一主宾 → 仍要写变量。写死的名字是一次性 Prompt，换一场就要重配。
- 抓不到称谓 → 必须给兜底词（「各位领导」），不要留空。

改写动作三：载体物理形态决定人设底色，不要只改名字。

第 196 轮把宇树 G1 的形态直接转成人设：「18 岁、少年感拉满的酷系极客男生」「外冷内热」「轻微傲娇」，并配「反差萌」——硬核人形外观站在粉色展台前。这不是装饰，是载体形态给的可用素材。

判断分支：

- 载体有明确物理特征（人形 / 轮式 / 小体积 / 大屏）→ 找一个能被自嘲或反差利用的点写进核心人设。
- 载体形态中性、无明显特征 → 不要硬编物理梗，转从业务场景找记忆点。

### 2.3 AGV 移动底盘：把地图写成白名单

改写动作：把所有可到达地点列成封闭清单，配固定播报格式，并给未入库地点一句一字不差的拒答。

原文（第 186 轮）：

```markdown
# 物理导航地点白名单与响应规则（最高优先级）
你的 AGV 地图系统中【仅收录】以下 3 个固定地点：
1. **前台**
2. **元宇宙**（或"元宇宙会议室"）
3. **教授办公室**

**导航执行规则（必须一字不差）**:
*   **白名单内地点**: 当用户提出前往上述 3 个地点的导航需求时，你【必须且只能】使用此固定格式回复："好的，正在为您导航到[目的地]。"
    *(示例: "好的，正在为您导航到元宇宙。" / "好的，正在为您导航到教授办公室。")*
*   **未知地点拒答**: 当用户要求导航到上述 3 个地点以外的任何位置（如财务室、茶水间等），你【必须一字不差地回复】："当前地点暂未入库，您可以联系工作人员后续进行补充。"
```

判断分支：

- 白名单固定话术必须与中控事件监听词对齐。原文指出这句话「通常作为硬件底盘的语音触发播报或中控事件（Event）监听词」，改一个字就可能不触发。
- 新增地点 → 先更新地图，再更新 Prompt 白名单，两边同步。只改一边必然出错。

### 2.4 自助贩卖机大屏：把停留时间写进字数

改写动作：同一套导览能力，在贩卖机上必须压缩，并加入带货转化位。

原文（第 190 轮）：

```markdown
**字数与首句控制**: 每次回答的第一句话【必须】是短句（控制在 10 字以内，且有标点）。考虑到游客在贩卖机前站立停留时间短，整段回复字数【严格限制在 120 个中文字符以内】。
```

同时补价格声明：

```markdown
**不随意承诺价格**: 贩卖机商品具体价格以机身屏幕标注的实时标价为准，不随意承诺未收录的特价优惠。
```

### 2.5 线上智能体 / IM 机器人 / 电话外呼

素材未覆盖。本次素材中「线上」「App」「智能客服」仅作为业务名词出现（第 101 轮产品线描述、第 182 轮知夏的岗位名），没有对应的 Prompt 正文、字数档位、触发方式。不要用线下载体的 120 字上限去套线上载体，也不要假定线上载体需要「纯台词禁令」——这条禁令的前提是有 TTS 播报和硬件中控，线上载体不一定具备。

## 三、字数：按「停留时长 + 是否要立刻行动」定档

不要按「屏幕 / 机器人」这种物理分类定字数。看素材里同一批 Prompt 的实际档位，规律是按人站着等多久、以及说完之后用户要不要马上做一个动作来定。

| 档位 | 素材出处 | 原文依据 |
|---|---|---|
| 60 字 | 大屏「知夏」C 端闲聊态 | 「回答干脆、俏皮、有梗，字数精炼在 60 字以内，绝不啰嗦。」 |
| 80 字 | AGV「小派」常规对话 | 「除开场白外，常规对话整段控制在 80 字以内，简明利落。」 |
| 120 字 | 机器人「小智」三场景、「西小岸」、「龙小灵」、宇树 G1 | 「避免听众站立聆听产生疲劳」「游客在贩卖机前站立停留时间短」 |
| 150 字 | 大屏「小智」专业汇报、「知夏」专业解答 | 「确保汇报干练、不拖泥带水」 |
| 80 单词 | 展台机器人「小白」英文回复 | 「英文回复控制在 80 个单词以内」 |

判断分支：

1. 用户站着、且听完必须立刻行动（AGV 前台登记、贩卖机下单）→ 80 字档。
2. 用户站着、纯听（展厅机器人讲解、美术馆导览）→ 120 字档。
3. 用户坐着或停留时间不受限、且内容是汇报（大屏数字人）→ 150 字档。
4. 闲聊、寒暄、接梗 → 60 字档，与业务解答分开写。

关键判断：一个 Prompt 里出现多个岗位或多个状态时，必须分状态给字数，不要给一个总数。知夏的做法是写死三档：

```markdown
**字数控制**: 闲聊态控制在 60 字以内；换岗出题控制在 120 字以内；专业业务解答（含联动话术）控制在 150 个中文字符以内。
```

不要用「尽量简短」「简洁一点」这类词。素材里所有生效的字数约束都带具体数字和单位（「120 个中文字符」），并且带上理由（「避免长者站立聆听产生疲劳」）。带理由的数字约束比裸数字更稳。

关于任务清单里提到的「线上 200 字」：素材未覆盖，本次切片没有任何 200 字档的样本或依据。不要为了凑档位编造 200 字档。

## 四、首句 10 字：跨载体通用的延迟对策

素材里所有带语音播报的载体都用了同一条，一字不改：

```markdown
**字数与首句控制**: 每次回答的第一句话【必须】是短句（控制在 10 字以内，且有标点）。
```

覆盖载体：大屏（小智、知夏）、机器人本体（小电、小智、西小岸、宇树 G1）、AGV（小派）、贩卖机（龙小灵）。

改写动作：

1. 无语音、纯文字输出的载体（素材未覆盖具体样本）→ 不要照搬这条，它解决的是首字上屏延迟，不是文字可读性。
2. 首句必须「有标点」。这条不能省。没有标点的短句会让 TTS 与断句逻辑拿不到切分点。

## 五、交互方式决定触发条件写法

### 5.1 文本暗号触发（无视觉载体唯一可靠的方式）

判断分支：大模型侧只能拿到用户发来的文本 → 全部用文本关键词做状态跳转，不要用空间位置、视觉状态、传感器读数。

写法要点（第 78 轮原文已验证）：

- 每个阶段给 2 到 3 个同义暗号，不要只给一个。「视频看完了」「去下一个展区」「继续接待任务」三条并列。
- 加一条全局禁令：「绝对不许自己提前输出后续阶段的台词。」
- 触发条件写「包含 X 的句子」，不写「用户说 X」。现场引导员不会一字不差念暗号。

### 5.2 触摸点击（大屏、自助设备）

大屏有屏幕，可以用「推荐问题」把高频意图前置成按钮，绕过语音识别的不可控。

原文（第 190 轮）：

```markdown
# 推荐问题（贩卖机大屏一键点击版）
建议在大屏下方配置以下 **4 个兼顾"导游"与"带货"的高频点击问题**：

*   **推荐问题 1**: "卢舍那大佛怎么走？"
*   **推荐问题 2**: "这台贩卖机有什么特色文创推荐？"
*   **推荐问题 3**: "今天景区天气怎么样？需要带伞吗？"
*   **推荐问题 4**: "离这里最近的卫生间和码头在哪？"
```

判断分支：

- 有屏幕且用户愿意抬手 → 配推荐问题，把「导览」和「转化」各占一半。
- 无屏幕（机器人本体、电话）→ 素材未覆盖点击路径，回到 5.1 文本暗号或语音。

### 5.3 语音唤醒：不写进 Prompt 的触发条件

第 77 轮初版把「当你被唤醒」写成阶段一的触发条件，第 78 轮全部改成文本指令。原因是唤醒词识别属于硬件与前端，大模型拿不到这个信号。

改写动作：唤醒逻辑交给硬件，Prompt 里只写「收到任意问候语（如：你好、启动、开始）即进入阶段一」。

### 5.4 扫码
素材未覆盖。本次切片没有扫码相关的触发设计。

## 六、动作与表情指令的隔离

这是跨载体改写里最容易出事的一段。判断标准：动作指令只在有身体、且动作由硬件执行的载体上有效；写进台词就是污染。

### 6.1 现象与代价

客户原始脚本里带硬件指令，模型会当成台词念出来：

> 您的脚本里有很多 `（机器人有A点移动到B点）`、`（指向展馆大屏）` 这种给硬件执行机构看的代码指令。

### 6.2 三段式禁令写法（可直接复用）

```markdown
**纯台词绝对禁令**: 【最高红线】你的回复【必须且只能】包含你要说出口的台词文字！【绝对禁止】在回复中输出任何括号（）或方括号 [] 及其中的物理动作指示（如：严禁输出"指向展馆大屏"、"机器人向B点移动"、"机器人退场"等字眼）。动作由硬件系统控制，你只管说台词！
**绝对纯文本输出**: 最终输出【绝对禁止】包含任何形式的 Markdown 标记符号（如加粗 **、标题 # 等）。
```

三段缺一不可：先说「只能输出什么」（正面定义），再列「禁止的形态」（括号、方括号），最后给「归属说明」（动作由硬件控制）。只写禁令不给归属，模型会觉得自己漏了信息，转而在正文里补描述。

### 6.3 中控接管场景：人设只覆盖自由对话段

判断分支：客户说「前面的对话用中控做」→ Prompt 里不要复写中控那几轮的台词，只写自由对话段的人设，并在禁令里点名中控已处理的动作。

用户原话（第 154 轮）：

> 第一个场景是下图所示，前面的对话我们会用中控做，后面自由对话的环节需要服合这个场景的人设设定

对应写法（原文）：

```markdown
**纯台词绝对禁令**: 【最高红线】你的回复【必须且只能】包含你要说出口的台词文字！【绝对禁止】在回复中输出任何括号（）或方括号 [] 及其中的物理动作指示（如：在自由对话阶段，绝对不能再输出"【太极展示】"或"（点头）"等字眼）。动作已由中控处理，你只负责说台词。
```

注意这里的禁令指名道姓写了「【太极展示】」——把中控脚本里的真实动作名写进禁令，比抽象说「不要输出动作」有效得多。

### 6.4 动作幅度本身也要从人设里删

用户原话（第 101 轮）：

> 不需要他跳舞，这个技能不要，避免展会上做很大幅度的动作

改写动作：删掉「舞蹈」「肢体表演」「才艺」类技能条目，并同步删掉 Few-Shot 里的相关示例。只删技能不删示例，示例会把技能带回来。

### 6.5 无身体载体

大屏数字人、贩卖机大屏同样保留「禁止括号描写」禁令，但理由不同：不是怕和硬件抢动作，是怕 TTS 把「（微笑着说）」念出来。原文用词是「你只输出需要通过语音播报的纯台词文字」。

线上、IM、电话 → 素材未覆盖是否保留此禁令。

## 七、组织方式：主 Prompt + 载体补丁

素材里出现三种组织形态，按场景选，不要混用。

### 7.1 共用基底 + 场景补丁（同一载体、多场景）

判据：载体不变、场景变（长者陪伴 / 科普讲解 / 沪剧搭档）。

做法：把「回复规范」「严格行为限制」整段固定为基底，一字不改；只替换 `# 角色`、`# 核心业务知识库`、`# 互动风格`。第 154、156、157 轮三个小智 Prompt 的回复规范段完全一致，只有角色与知识库不同。

可复用基底（三段，跨场景稳定）：

```markdown
**纯台词绝对禁令**: 【最高红线】你的回复【必须且只能】包含你要说出口的台词文字！【绝对禁止】在回复中输出任何括号（）或方括号 [] 及其中的物理动作指示。动作由中控控制，你只负责说台词。
**绝对纯文本输出**: 最终输出结果中【绝对禁止】包含任何形式的 Markdown 标记符号（如加粗 **、标题 # 等），输出必须是纯文本。
**字数与首句控制**: 每次回答的第一句话【必须】是短句（控制在 10 字以内，且有标点）。整段回复字数【严格限制在 120 个中文字符以内】。
```

补丁内容只需三处：角色定位一句、知识库清单、边界禁区。

### 7.2 单 Prompt 多岗位状态机（同一载体、多业务身份）

判据：载体不变（一块大屏），但要在同一场演示里演示多个岗位（企业前台 / 机场导览 / 智能客服）。

做法：不拆成三个 Prompt，写成一个 Prompt 里四个状态，各自绑定字数与话术。

```markdown
**状态一：C端元气闲聊态（默认状态）**
- **触发场景**: 日常问候、打听个人信息（星座、爱好、穿搭）、闲聊八卦、吐槽心情。
- **交互口吻**: 保持 23 岁甜飒社牛本色，回答干脆、俏皮、有梗，字数精炼在 60 字以内，绝不啰嗦。

**状态三：B端场景切换与主动抛题引导（核心演示亮点）**
- **触发场景**: 当用户说出指定岗位（如"切换到企业前台"、"我想看机场导览"、"做智能客服"）时。
- **执行规则**: 
  1. 瞬间变装换岗，确认身份切换。
  2. 立即将语调切换为对应岗位的专业口吻。
  3. 【必须主动抛出 2 个测试问题】，引导用户对你进行提问！
```

判断分支：

- 演示需要展示「一机多能」→ 用状态机，并把「主动出题」写进规则。这是知夏那段最关键的补丁：切岗后必须给用户两个可点的测试问题，否则现场没人知道该问什么。
- 三个岗位要分别部署给三个真实业务部门 → 拆成三份 Prompt，用 7.1 的基底。

### 7.3 跨载体交接双 Prompt（机器人 → 大屏）

判据：现场有两个物理载体要接力（机器人引导到 B 区，唤醒大屏数字人汇报）。

做法：两个 Prompt 共享同一段交接台词，机器人侧负责「叫醒对方」并把称谓传过去，大屏侧负责「接住称谓开始汇报」。

机器人侧（第 109 轮原文）：

```markdown
**阶段四：B区大屏引入与"小智"唤醒**
*   **触发文本暗号**: 引导员发送包含【"介绍数字人"】、【"唤醒小智"】或【"到了B区"】的句子。
*   **你的唯一回复**: "`[称谓]`，各位领导，上海公司目前也在积极进行数字人方面的探索与研究，我们打造的数字人小智，已经打通了具身机器人与数字人之间的连接通道，使得我和小智之间的沟通更为顺畅。你好，小智。小智，今天来到我们展台的是某能源企业公司的`[称谓]`及各位领导，接下来请你开始汇报吧。"
```

大屏侧对应写「尊称锁定」：

```markdown
**尊称锁定**: 在对话中，对主宾必须尊称为"王总"（或根据引导员介绍的实际职务），称呼其他随行嘉宾为"各位领导"、"各位同仁"。
```

判断分支：

- 两个载体的称谓变量必须用同一个兜底规则（抓不到就用「各位领导」），否则交接时会掉称谓。
- 同一批部署时，两个 Prompt 的风格基线必须一致。第 109 轮明确因为「某能源央企是特大型央企」，两个智能体统一去掉「有梗/幽默」的网络语调。载体不同但客户不同时，风格基线跟着客户走，不跟着载体走。

素材未覆盖：以文件形式把主 Prompt 与补丁拆开管理（补丁文件、版本号、加载顺序）。本次素材里的补丁都是同一份 Prompt 内的段落替换。

## 八、一个载体要交付四个独立产物，不要全塞进主 Prompt

素材里反复出现的是四件分开配置的东西，混在一起会让模型把展示话术当业务话术说。

1. **人设标签**（B 端销售展示用，不进对话 Prompt）。第 196 轮明确标注「人设标签描述（B端展示用）」。模板是「专精 X 场景，提供 Y 能力，具备 Z 调性」：

```markdown
**标签**: "专精 AI 开发者生态与极客嘉年华导览场景，提供全套活动部落动线与硬核具身智能技术指引，具备潮酷洒脱的少年极客服务调性。"
```

2. **开场白**（平台的开场白字段，不进主 Prompt 正文）。第 102 轮原话：「您可以直接复制下方灰色框内的内容配置到智能体的"开场白"后台」。

开场白黄金模板（第 104 轮由客户提供的参照）：

> 您好，我是机场枢纽智能总管航小达，赶路别慌，查航班、找登机口、过安检遇难题，随时叫我。

结构拆解：身份 + 情感安抚 + 三件核心事 + 随时叫我。套用后的成品：

```markdown
"您好！我是某科技公司展位智能管家小白。逛展别迷路，找展位、问技术、体验黑科技遇难题，随时叫我。"
```

同一个模板换载体只换中间三件事（第 105 轮企业前台版）：

```markdown
"您好！我是某科技公司的智能前台管家小白。来访别客气，找同事、办登记、送快递外卖遇难题，随时叫我。"
```

3. **主 Prompt**（角色、知识库、回复规范、行为限制）。

4. **推荐问题**（仅大屏类载体，见 5.2）。

判断分支：开场白里不要念技术黑话。第 103 轮客户直接否掉：「不用明确的说什么AIGC视频生成这种」。改成「咱们展区有超多好玩的 AI 体验，有什么我可以帮您的吗？」。

## 九、能力声明：载体切换时必须重写「做不到的事」

这是换载体时最容易漏改的一段。同一个人设，在大屏上做不到的事，在 AGV 上做得到，反之亦然。

### 9.1 先列能力对照

判断分支：

1. 能移动 → 可承诺带路，但只承诺白名单内地点。
2. 不能移动 → 只口述路线 + 引流。
3. 能联网 → 可承诺实时查询，但必须先给过渡语（见第十节）。
4. 不能联网 → 不承诺「实时」「最新」，改口为「以现场标注为准」。
5. 只能卖软件不卖硬件 → 写「服务边界声明」。第 101 轮原文：「小白只提供"智能与表达的中枢系统（表情/语音/对话）"，【绝对不卖机器人硬件，不做运动控制】。」

### 9.2 大屏：不承诺带路

见 2.1。要点是给一句固定引流话术，把「做不到」转成「隔壁能做」。

### 9.3 AGV：不承诺地图外地点

见 2.3。拒答必须一字不差，不能换说法。

### 9.4 贩卖机：不承诺价格

见 2.4。

### 9.5 展台 / 前台：把商务问题挡在固定口径后面

第 101 轮的四条标准回答值得整段复用，载体是机器人本体：

```markdown
1. **涉及商务与转人工问题（价格、折扣、合同、周期承诺、私有化部署、定制形象费、系统架构、参数、招聘等）**:
   - *唯一标准回答*: "这个问题需要结合您的具体情况由相关同事进一步确认。我可以先帮您记录需求，并为您对接对应团队。"
2. **信息无法确认时（知识库无记录）**:
   - *唯一标准回答*: "关于这一点，我目前没有足够的信息给出准确答复。为了避免提供错误信息，建议由相关同事进一步为您确认。"
3. **涉及竞争对手对比/贬低时**:
   - *唯一标准回答*: "不同产品在定位、技术路径和应用场景上各有侧重。某科技公司的特点是围绕具身交互智能，打通感知、认知、表达和运控，同时通过某内容创作平台提供知识理解、内容创作和智能体能力。具体选择还需要结合您的业务需求进行判断。"
4. **涉及保密与敏感信息（合同金额、未公开客户、研发规划）**:
   - *唯一标准回答*: "相关内容可能涉及未公开或保密信息，我无法直接提供。您可以通过正式渠道与相关团队进一步沟通。"
```

写法要点：给「唯一标准回答」而不是「参考话术」，并加「【绝对禁止】进行任何字句修改」。现场演示时改一个字就可能变成承诺。

### 9.6 国企 / 央企客户的载体基线

用户原话（第 109 轮）：

> 因为是国企，所以需要风格上严谨一些。不需要在Prompt里面内置知识库。

两个动作同时做：去掉网络语调；知识库外挂不内嵌。

```markdown
**严谨专业第一**: 语气沉稳、大气、得体。使用标准的电力行业术语。绝对禁止使用任何网络流行语、轻浮表述或娱乐化语言。
**唯一信息来源**: 你的所有业务解答、技术参数【必须】严格依托你所挂载的知识库。如遇到知识库以外的问题，必须礼貌克制地回应，决不瞎编。
```

判断分支：

- 客户是央企 / 政府 / 医疗 → 严谨基线 + 统一拒答口径 + 知识库外挂。
- 客户是极客大会 / 消费品牌 → 可放开口头禅与自嘲，见 2.2 宇树 G1。
- 同一批里既有严谨载体又有活泼载体 → 以客户为准，不以载体为准。

## 十、延迟敏感场景的短句策略

素材给出四层手段，从前往后依次加，不要只加最后一层。

1. **首句 10 字内 + 有标点**（见第四节）。先给反应，再给内容。
2. **整段压到 120 字以内**。原文明确换算过：120 字「让语音播报在 8~10 秒内迅速完成」。
3. **插件调用前强制输出过渡句**。这是素材里最实用的一条，第 182 轮客户主动提出：

> 在机场场景，我问目的地天气，比如我要去北京，北京现在天气怎么样，他需要调用BochaAISearch的联网插件进行天气查询，同时先输出一个过渡词：现在正在为您查询天气，请稍后。然后再同步联网查询的天气结果

落地写法：

```markdown
**规则 2：机场目的地天气与插件过渡词**: 当在机场场景中，用户询问目的地天气（如"我要去北京，北京天气怎么样"），你【必须调用 BochaAISearch 插件】联网查询。输出回复时，开头【必须先输出固定过渡句】："现在正在为您查询天气，请稍后。"紧接着再输出插件查到的实时天气与出行温馨提示。
```

对应的设计说明（原文）：能「极大缓解插件调用带来的 1~2 秒延迟等待感」。

4. **去列表化**。数字序号会让 TTS 念「一、二、三」并产生多余停顿。原文：

```markdown
**去列表化处理**: 介绍楼层或设施时，【必须】转化为使用"首先、其次、另外"或自然口语连接的段落，严禁使用"1. 2. 3."数字序号列点。
```

判断分支：

- 有插件 / 联网 / 外部 API → 必须配过渡句，且过渡句要写死成一字不差的固定句。
- 无外部调用、纯知识库 → 不需要过渡句，压字数即可。
- 载体本身有端侧渲染、延迟已很低 → 仍保留过渡句。素材里「端到端响应<2秒」是宣传参数，不是每台现场设备的实测值，不能拿它替代过渡句。

## 十一、切换载体时的改写检查清单

按顺序过一遍，每项都要能指到 Prompt 里的一句具体话。

1. 这个载体能不能移动？不能 → 删掉所有带路承诺，加引流话术。
2. 大模型侧能拿到什么输入？只有文本 → 触发条件全部改成文本暗号，删掉空间/视觉条件。
3. 动作由谁执行？硬件中控 → 加三段式纯台词禁令，并把中控真实动作名写进禁令。
4. 有没有中控已覆盖的前置轮次？有 → 人设只写自由对话段，不复写中控台词。
5. 人名 / 称谓是不是写死的？是 → 改成变量抓取 + 兜底词。
6. 字数档位对不对？按第三节的停留时长判断分支重定，分状态给不同数字。
7. 首句 10 字内 + 有标点这条在不在？
8. 有没有外部调用？有 → 加固定过渡句。
9. 有没有做不到的能力被写进人设？逐条对照第九节。
10. 开场白、人设标签、推荐问题是不是被塞进主 Prompt 了？是 → 拆出来单独配。
11. 同一批多载体部署时，风格基线是不是统一的？按客户定，不按载体定。
12. 换载体后 Few-Shot 示例改了吗？没改 → 示例会把旧载体的行为带回来。
13. 素材未覆盖的载体（线上、IM、电话）不要套用本清单第 1、3、4、8 项，其前提是有身体或现场中控。
