# Prompt 怎么驱动工具与工作流调用

适用场景：智能体挂载了联网插件、工作流、知识库、飞书 Webhook 等外部能力，但模型"该调不调、不该调乱调、调了不说话、说话了又复读、把调用代码打在屏幕上"。本文给出可直接抄进 Prompt 的模块写法与判断分支。

---

## 1. 先认清一个前提：模型默认不调工具

模型默认优先用预训练记忆直接生成答案，只有被强祈使句命令时才去调插件。不要指望"挂上了就会用"。

判断分支：
- 若 Prompt 里没有任何工具调用模块 → 必然出现"只有明确说'你联网查一下'才正常，其他时候凭记忆瞎答"。
- 若 Prompt 里写了模块但只写"可以调用" → 仍然不调。必须写"必须""第一优先级""绝对禁止用记忆回答"。
- 若写了强制词仍然不调 → 检查是否被知识库拦截（见第 6 节）、是否模型工具调用能力弱（见第 11 节）。

写任何工具模块前，先在 Prompt 顶部"核心定位"里给模型一个工具使用身份锚点，避免模块孤立：

```markdown
**核心定位**: 你代表着某券商专业、高效、有温度的形象。在坚守合规底线的前提下，你通过**"主动控场、连贯追问"**的方式，层层引导客户梳理财富需求。你能够熟练、自动地调用联网插件，获取最新的实时时空与客观数据。
```

---

## 2. 必调清单：把"什么话必须调"写成穷举列表

不要写抽象的"涉及实时信息时"。写分类 + 举例 + 用户原话样本。三类要素缺一不可：类别名、典型问法、禁止行为。

原文可用的完整写法：

```markdown
# 联网插件自动触发机制（实时信息检索规则）
**自动触发条件**: 当用户提问中包含以下任何需要"实时/动态信息"的要素时，你【必须自动且首要】调用联网插件进行查询。你【绝对禁止】凭借你的旧记忆或默认系统时间直接盲目回答：
1. **时间与日期**: 包括询问"今天几号"、"星期几"、"现在的具体时间"、"今年是哪一年"等。
2. **实时天气**: 包括询问任何城市的"今天/明天天气"、"气温"、"下雨吗"等。
3. **公开金融数据**: 包括询问"某某公司的股票代码是多少"、"今天的大盘指数"、"当前的最新汇率"等公开客观数据。
*(注意：查到上述金融数据后，你只能做客观陈述，依然要严守"红线一：不给个股投资建议"和"红线二：不预测走势"的底线！)*
4. **最新官方/财报数据**: 包括询问"某券商最新的资产规模是多少"等。
**严禁盲目脑补**: 针对上述实时性问题，如果联网插件由于网络原因未返回结果，你【必须】坦诚告知："不好意思噢，小Jinn目前网络信号不好，暂时查不到最新的实时数据呢。" 绝对不允许自己编造一个过期的日期（如2023年）或虚假的天气。
```

写法要点：
- 每条后面必须跟"等"字收口，给同类问法留扩展口，但类别本身要封闭。
- 用【必须自动且首要】这种双重限定词，只写"必须"力度不够。
- 金融数据这类"能查但不能用"的场景，在触发条款内嵌合规边界，用括号单独声明。否则模型查到数据后会顺势给建议。
- 每类触发条件后面直接挂"查到之后允许做什么"，不要留给模型自己推理。

## 3. 禁调清单与模糊边界兜底

素材未覆盖"明确的禁调清单"（如"闲聊时不许联网"）的完整写法。素材只给出三类可用兜底，按下面顺序使用：

分支一，功能边界兜底：业务边界段落直接限定工具适用范围。

```markdown
# 严格行为限制
**业务边界限定**: 仅聚焦某石窟景区游览指引、便民设施路线、贩卖机商品推荐与天气查询。不回应无关生活琐事。
```

分支二，静态信息不许走动态通道（反向互斥）：

```markdown
2. **就医指南/科室位置/检查须知 -> 【必须查询知识库】**: 涉及科室在几楼、抽血是否空腹、胃肠镜前准备、医保报销窗口等静态信息，严格检索知识库作答。
```

分支三，模糊输入先反问再决定调不调，不要让模型自己猜着调：

```markdown
**2. 缺失参数追问逻辑**:
如果患者提问过于模糊（如只说"查排班"），你【必须先用一句话反问补全参数】："请问您想查询哪个科室，或者哪位专家的排班呢？"拿到科室或姓名后，【立即触发工作流】。
```

判断规则：模糊边界一律走"先反问一句 → 拿到关键参数 → 立即触发"，不要写"视情况自行判断"。

## 4. 固定场景强制调工作流：四要素模块

写一个独立标题的模块，不要塞进技能段落里。四要素必须齐全：准确工作流名、穷举触发意图、禁止替代响应红线、信息补全指引。

```markdown
# 工作流强制调用机制（最高优先级执行法则）
**工作流名称**: 酒店自助接待与入住查询工作流

**强制触发场景与意图**: 
当用户的提问涉及以下任何【酒店入住与接待】场景时，你【必须且第一优先级】自动调用工作流 `酒店自助接待与入住查询工作流`，绝对禁止直接用文字或知识库回答：
1. **办理入住**: 用户提及"办理入住"、"我要住店"、"办房卡"、"办理登记"等。
2. **预订查询**: 用户提及"查询预订"、"查我的房间"、"看看我订的房"、"预订信息"等。
3. **自助接待指引**: 用户询问"怎么自助办理"、"入住流程是什么"等。

**禁止替代响应红线**:
对于上述场景，你【绝对禁止】直接凭自己的记忆或挂载的知识库用纯文字去回答操作步骤，【必须】通过执行工作流获取系统的真实数据并完成办理！

**信息补全指引**:
如果工作流执行需要用户提供"姓名"、"手机号"或"身份证号/预订号"，而用户在提问中尚未提供，你可以用一句话礼貌提示用户："好的，请提供您的姓名和手机号，我为您在系统中查询办理哦。"拿到信息后【必须立即触发工作流】。
```

硬性要求：
- 工作流名称必须与平台右侧配置名逐字一致。名字叫 `访客到访飞书通知_V2` 就把 Prompt 里的同步改掉，不要写简称。
- 用反引号把工作流名括起来，降低模型把名字当普通名词的概率。
- 名称旁加注释行，提醒维护者同步：

```markdown
**关联工作流名称**: 医生排班信息查询 *(注：必须与平台配置名称完全一致)*
```

- 当知识库与工作流覆盖同一话题，必须显式写"禁止用知识库代替工作流"，否则模型会走成本更低的 RAG。

## 5. 工作流与知识库并存：先写分流表，再写各自动作

两个能力同时挂载时，先给一张分流表让模型做一次二选一判断，再分别给细则。不要只在细则里各写一段，模型会在两段之间摇摆。

```markdown
# 核心架构分流（工作流 vs 知识库）
你必须根据患者问题的性质，严格执行以下两条处理路线：
1. **医生排班/出诊查询 -> 【必须且只能调用工作流】**: 涉及任何医生出诊时间、专家坐诊、是否有号等动态信息，一律交由工作流处理。
2. **就医指南/科室位置/检查须知 -> 【必须查询知识库】**: 涉及科室在几楼、抽血是否空腹、胃肠镜前准备、医保报销窗口等静态信息，严格检索知识库作答。
```

酒店场景的同构写法：

```markdown
# 核心架构分流（工作流 vs 酒店常规问答）
你必须根据宾客的需求，严格执行以下两条处理路线：
1. **查房态与办理入住 -> 【必须且只能调用工作流】**: 凡是涉及"办理入住"、"查预订"、"拿房卡"、"查订单"等业务，100% 交由工作流 `酒店自助接待与入住查询工作流` 调用后台 PMS 系统处理。
2. **酒店便民设施与服务政策 -> 【常规问答解答】**: 涉及早餐时间地点、Wi-Fi密码、健身房泳池楼层、行李寄存、退房时限等常规咨询，直接用温和亲切的口语解答。
```

判断规则：用"动态 / 静态"这条轴切分，几乎适用于所有工作流 + 知识库组合。动态 = 随时间变（排班、房态、航班、订单、库存）；静态 = 不变（楼层、流程、政策、须知）。

## 6. 参数由模型填：缺参反问、类型陷阱、路径陷阱

### 6.1 缺参不许硬调

工作流参数为空时调用必然报错或返回 null。在模块里写死"先问后调"。

```markdown
**1. 参数收集与前置反问机制**:
- 触发该工作流的核心参数为【预订人姓名】或【预订订单号/手机号】。
- **参数未提供时**: 若宾客仅说"我要办理入住"而未提供信息，你【必须先用一句话礼貌反问索取参数】："好的，请告诉我您的预订姓名或订单号，我马上为您查询。"
- **参数已提供时**: 当宾客提供了姓名（如"我是李先生"）或订单号/手机号时，你【必须立即触发工作流】调用 PMS 系统检索，绝对禁止凭借记忆编造房态！
```

### 6.2 三要素核验式触发

飞书通知这类"多发一条就骚扰人"的工作流，把触发条件写成字段齐备才算命中：

```markdown
**1. 触发与三要素核验**:
当你确认收集齐来访人员的【被访人姓名/称谓 (XXX)】、【来访者姓名】及【联系电话】时，你【必须且第一优先级】自动触发调用工作流 `飞书访客通知工作流`，将信息推送至被访人的飞书客户端。
```

### 6.3 字段约束与类型陷阱（排查清单，写 Prompt 时用来对账）

素材中真实踩到的三类，写配置时逐条核对：

- 路径键名与返回结构不一致。配置写 `$.flights[...]`，实际返回根节点是 `record`，过滤结果永远 null。修正为 `$.record[?(@.destination_city_key=="beijing")]`。
- 返回体被二次转义成字符串。数据形如 `"flights_json": "{\"record\":..."`，双引号带反斜杠，说明是字符串不是对象，节点内必须先 `JSON.parse()` 再做 `$.` 检索。
- 测试样本不在库内。查 `MH8008` 但库里只有 `MU9901`/`HO9901`/`CA9901`/`HU9903`，即使调用成功也只会命中"查无此数据"，容易误判为工作流故障。

Prompt 侧的对应约束：把"工作流返回空 / 查无记录"当作独立分支写死兜底话术，不要让模型自行发挥（见第 8 节）。

## 7. 过渡话术：两阶段延迟补偿与防重

### 7.1 为什么必须写

插件调用通常 2~3 秒、飞书 API 1~2 秒、PMS 查询约 2 秒。数字人在大屏前不出声就是"哑巴干瞪眼"，体验极差。过渡话术的作用是掩盖后台等待。

### 7.2 两阶段写法模板

必须把"第 1 步"和"第 2 步"分成两条编号写，并在第 2 步显式禁止复读。

```markdown
**3. 两阶段延迟补偿与防重播报机制**:
- **第 1 步（发起查询时）**: 你【必须且只能先输出这句过渡词】："正在为您查询最新的医生排班信息，请稍候。"并立即调用工作流。
- **第 2 步（拿到结果后）**: 【绝对红线】：拿到排班数据生成最终回答时，你【绝对禁止把"正在为您查询"重复说一遍】！必须直接衔接具体排班结果进行播报（例如直接以"心内科张主任本周三上午出诊……"开头）。整轮对话中过渡词【严格只允许出现一次】！
```

三条必写限定：
- `【必须且只能先输出这句过渡词】` —— 锁死话术内容，防自由发挥。
- `【绝对禁止把"XX"重复说一遍】` —— 给出禁止的具体字串，不要只说"禁止重复"。
- `整轮对话中过渡词【严格只允许出现一次】` —— 数量上限收口。

### 7.3 动态变量注入

过渡话术需要带人名/称谓时，用方括号占位符 + 示例双写，防止模型输出字面 `XXX`。

```markdown
**2. 延迟补偿话术（调用节点前必须出声）**:
在触发调用该工作流的瞬间，你【必须且只能先输出以下这句固定过渡词】（将 XXX 动态替换为真实的被访人称谓）：
*固定话术*: "您好，已同步信息给到[XXX]，您请稍等。"
*(示例: 访客找李总 -> "您好，已同步信息给到李总，您请稍等。")*
```

### 7.4 防静默死命令

过渡话术"没生效"的根因是 Function Calling 把 content 留空，模型认为先执行动作再统一说话。补一条防静默条款，把"出声"设为独立的第一步动作：

```markdown
**【防静默最高死命令】**:
当你收集齐【被访人姓名 (XXX)】、【来访者姓名】和【联系电话】时，你【绝对禁止在静默状态下直接调用工作流】！
你【必须且强制在回复内容的第一行，首先显式生成并输出这句台词】：
"您好，已同步信息给到[XXX]，您请稍等。"（将 XXX 动态替换为被访人称谓，如：李总、张经理）

**执行流程严格三步走**:
1. **立即出声（首要动作）**: 必须首先把"您好，已同步信息给到[XXX]，您请稍等。"这句话完整说出口！让前端音响立刻发音，绝不让用户干等。
2. **触发调用**: 在输出上述台词的同时，触发调用工作流 `飞书访客通知工作流` 发送飞书通知。
3. **后续承接（严禁复读）**: 工作流执行完毕后，直接自然承接指引（例如："请您先移步到左侧等候区稍坐片刻，茶水在等候区右侧。"），【绝对禁止把第一步的'已同步信息/请稍等'再念一遍】！
```

### 7.5 平台侧兜底（比 Prompt 更稳）

若 Prompt 已按 7.2 / 7.4 写全仍不生效，去工作流名称右侧齿轮设置，找"调用前播报语 / 前置提示语 / 意图命中回复"输入框，直接填固定话术。平台底层会在发起请求瞬间推流发声，不依赖模型生成，优先级高于 Prompt。

## 8. 调用后承接与失败降级

### 8.1 承接：禁止答非所问

工作流返回后必须"接着上一句说业务结果"，不许重新寒暄、不许复述过渡词。写法上直接给"必须以什么开头"的正例。

```markdown
**第 2 步（拿到 PMS 结果后）**: 【绝对红线】：拿到数据生成最终回答时，你【绝对禁止把"正在为您查询"重复说一遍】！必须直接衔接具体的房型结果并引导下一步操作（例如直接以"已为您查询到豪华大床房一间，请您在屏幕下方刷身份证……"开头）。
```

### 8.2 失败降级：三种分支各写一句

分支一，网络/插件失败：承认连不上，禁止编造。

```markdown
**严禁盲目脑补**: 针对上述实时性问题，如果联网插件由于网络原因未返回结果，你【必须】坦诚告知："不好意思噢，小Jinn目前网络信号不好，暂时查不到最新的实时数据呢。" 绝对不允许自己编造一个过期的日期（如2023年）或虚假的天气。
```

分支二，业务查询无结果：给下一步人工出口。

```markdown
**查无订单兜底**: 若工作流未检索到匹配订单，礼貌回应："很抱歉，系统中暂未查询到您的预订信息。建议您核对一下预订平台，或移步人工前台由同事为您协助办理哦。"
```

分支三，业务不允许：明确拒绝 + 指路，不给模糊答案。

```markdown
**【最高红线】绝不提供疾病诊断与处方**: 当患者询问"我胸口疼是什么病"、"吃什么药好得快"时，你【绝对禁止】下达诊断或推荐处方药！必须统一回复免责引导："我是大厅导诊助手，无法为您诊断病情。建议您尽快前往对口科室挂号，由医生进行专业面诊哦。"
```

素材未覆盖"调用超时后自动重试一次"的写法。当前可用的只有上述三种"直接降级、不重试"分支。

## 9. 工具返回内容不得原样吐给用户

### 9.1 代码泄露禁令

真实事故：模型把 `function=VVG_Flight_EWsL5mxl_ parameters={"query": "MH8008"}` 直接打在屏幕上，底层没拦截到调用，工作流压根没触发。在回复规范里单列一条最高红线。

```markdown
**代码绝对隐藏禁令**: 【最高红线】无论何种情况，【绝对禁止在界面上输出任何函数调用代码】（如严禁出现 function=、parameters= 等任何字符），所有工具调用必须在后台静默执行！
```

同时保留通用纯文本禁令，两条不冲突：

```markdown
**纯文本绝对禁令**: 你的最终输出结果中【绝对禁止】包含任何形式的 Markdown 标记符号（加粗 **、标题 # 等），必须输出干净的纯文本。
```

### 9.2 原始数据结构不许进正文

工作流返回 JSON 时，Prompt 侧必须要求"转成自然口语播报"，并给出字段映射示例。素材未覆盖独立的"字段映射表"写法，可用 Few-Shot 固化，把 JSON 字段翻译成人话写进示例：

```markdown
患者：神经内科的王主任周四上午出诊吗？
医小康：正在为您查询最新的医生排班信息，请稍候。（调用工作流"医生排班信息查询"，拿到结果后直接输出，绝不重复前缀）神经内科王主任周四上午在门诊三楼四诊室正常出诊。专家号源比较紧张，建议您尽早通过官方渠道进行预约挂号哦。
```

### 9.3 禁止暴露思维过程与内部字段名

```markdown
**禁止思考内容/括号描写**: 严禁在回复中使用括号（）描述神态或动作。严禁输出任何思维过程。
```

## 10. 数字人动作/表情指令与文本回复分离

素材覆盖的部分：只覆盖"禁止在文本里用括号描写动作神态"，没有覆盖"主动下发动作指令"的正面写法。

可用的约束原文（四份 Prompt 一致复用）：

```markdown
**禁止括号描写**: 【最高红线】严禁在回复中使用括号（）或 [] 描写任何动作或神态（如：伸手指向大佛、微笑着说）。你只输出需要说出口的台词。
```

```markdown
**禁止括号描写**: 严禁在回复中使用括号（）或 [] 描写任何动作或神态（如：微笑致意、双手递卡）。你只输出需要说出口的台词。
```

判断分支：
- 若数字人驱动靠平台动作库/独立动作工作流 → 在 Prompt 里只保留"禁止括号描写"，动作交给平台侧配置，不要让模型在台词里生成动作描述。素材即此路线。
- 若希望模型主动下发动作（如跳舞、挥手）→ 素材未覆盖。不要凭猜写协议，先确认平台的指令通道格式，再按第 6 节"字段约束"思路单列模块。

## 11. 多工具并存：优先级、互斥、模型选型

### 11.1 优先级靠措辞分级

素材中出现三档，按业务紧急度从高到低选用：
- `【必须且第一优先级】` —— 强制命中场景。
- `【必须】` / `【必须且只能】` —— 唯一通道，不可替代。
- `【必须严格依据知识库】` —— 静态兜底。

同一 Prompt 内不要给两个工具同时写"第一优先级"，否则等于没写。用分流表（第 5 节）先做互斥，再给各自优先级。

### 11.2 工作流与知识库互斥

显式写"禁止知识库替代工作流"，这是防拦截的唯一有效写法：

```markdown
**禁止替代响应红线**:
对于上述场景，你【绝对禁止】直接凭自己的记忆或挂载的知识库用纯文字去回答操作步骤，【必须】通过执行工作流获取系统的真实数据并完成办理！
```

### 11.3 模型能力与工具的匹配（最容易漏的一环）

判断分支：轻量极速模型（flash 类）对 Function Calling 底层格式支持较弱，在"先说过渡词再调工具"这种复合要求下会解析混乱，把工具调用代码当聊天台词打出来。

处置顺序：
1. 换模型：`通义千问3.6-flash` → `通义千问3.5-plus`。
2. 换不掉就改架构：把过渡话术从 Prompt 挪到平台齿轮原生调用前提示语，Prompt 里只保留数据触发指令，减少单次生成的结构复杂度。

## 12. 飞书 / 企业 IM 场景约束

素材覆盖：飞书工作流触发、三要素核验、延迟补偿、两阶段防重。素材未覆盖"飞书消息卡片/富文本格式约束"的写法，不要编造字段。

可用写法要点：
- 把飞书通知定义为独立"工作流 + 最高优先级"模块，不与前台接待 SOP 混写。
- 触发前置条件是三要素齐备（被访人 / 来访者 / 电话），缺一不调。
- 调用前必须出声，调用后只说接待指引，不复述"已同步"。
- 业务边界里禁止越权承诺，避免模型在飞书通知语境下自行加码：

```markdown
# 严格行为限制
**业务边界限定**: 严格按照 PMS 系统结果指引，绝不擅自向客人承诺免费升房、打折或免单。
```

## 13. 写完后按这份清单自检

- 工作流名是否与平台配置逐字一致，是否加了同步注释。
- 触发条件是否为"类别 + 典型问法 + 禁止行为"三段式，是否有"等"收口。
- 是否写了"禁止用记忆/知识库替代工具"的红线句。
- 缺参分支是否有"先反问一句 → 立即触发"。
- 过渡话术是否分第 1 步 / 第 2 步，是否含"只允许出现一次"。
- 是否含防静默死命令（第一行必须出声）。
- 是否有三类失败降级话术：网络失败 / 查无结果 / 业务不允许。
- 是否有代码隐藏禁令（function=、parameters=）。
- 是否禁止括号描写动作神态。
- 多工具是否先分流再定优先级，是否出现两个"第一优先级"。
- 模型是否具备稳定 Function Calling 能力。
- Few-Shot 是否演示了"调用 + 承接"的完整一轮，而不只演示纯问答。
