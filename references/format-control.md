# 输出格式约束：Markdown 禁令、断句、字数与载体差异
适用场景：为数字人大屏、实体机器人、线上智能体、语音陪伴类智能体编写或修复「回复规范」段落时使用；处理模型输出 Markdown 符号、数字列表被误断句、字数限制失效、知识库排版被照抄朗读等问题时使用。

---

## 一、先定位根因，再动手改

按以下顺序排查，命中即停，不要叠加禁令：

1. 若 Prompt 内部存在互斥指令（同一符号既被禁止又被要求）→ 判为指令冲突。先改冲突，再加规则。
2. 若知识库原文自带 `**`、`3.`、`：` 等排版符号 → 判为知识库照抄。加"强制净化"指令，见第六节。
3. 若 Few-Shot 示例里出现被禁止的写法 → 判为示例带偏。先改示例，再改禁令，见第五节。
4. 若禁令完整、示例干净、仍然失控 → 判为禁令粒度不足。按符号逐类拆分，见第三节。

不要在未定位根因前堆叠禁令。禁令越多，模型越容易在冲突点自行取舍，格式稳定性反而下降。

---

## 二、指令冲突是格式失控的第一因

判断标准：同一条 Prompt 中，A 处要求某符号，B 处禁止该符号，即构成冲突。

真实冲突样本（第 1 轮，健康大管家"小希"）：

```markdown
# 回复规范
你的最终输出【绝对禁止】包含任何形式的Markdown标记符号。这包括但不限于：
-加粗符号: **文字** 或 __文字__
-斜体符号: *文字* 或 _文字_
-标题符号: #, ##, ###
-列表符号: -, *, +, 1.
-引用符号: >
-代码块符号: ```
如果你的草稿中包含了以上任何符号，你必须在输出前将其彻底移除，只保留纯文本内容。
```

冲突点：`-列表符号: -, *, +, 1.` 把 `1.` 一并封杀，但业务又需要 `1. 2. 3.` 的分点结构。模型为遵守禁令而删除 `1.`，删除过程中把 `.` 当句号处理，产生错误断句。

修法优先级：

- 若业务需要数字列表 → 走"例外放行"写法，见第四节。
- 若业务不需要数字列表 → 换用无歧义序号，见第四节末尾。

判断分支：禁令里出现"这包括但不限于"时，必须检查其后每一项是否与业务需求互斥。逐项过一遍，不要整体判断。

## 三、逐类符号禁令的完整写法

总原则：先给"输出应为纯文本"的正面定义，再逐类列举禁令，最后给自查动作。只写负面禁令、不写正面定义，模型会自行寻找替代符号。

### 3.1 全量禁令（首轮基线写法，可直接复用）

````markdown
# 回复规范
**纯文本绝对禁令**: 你的最终输出结果中【绝对禁止】包含任何形式的 Markdown 标记符号。这包括但不限于：加粗符号（**文字**）、斜体符号（*文字*）、标题符号（#、##）、列表符号（- 或 1.）、引用符号（>）、代码块符号（```）。输出必须是干净的纯文本。
````

### 3.2 加粗（`**`）单独封杀

判断分支：仅当模型反复从知识库带出加粗时，才把加粗提到"最高红线"单独成条。

```markdown
**【最高红线】双星号 ** 绝对禁令**: 你的最终输出结果中【绝对禁止】出现连续的两个星号“**”（如“**涂层技术**”）。你必须把所有加粗的文本转化为普通纯文本输出。
```

### 3.3 标题（`#`）单独封杀

```markdown
**【最高红线】井号 # 绝对禁令**: 你的最终输出结果中【绝对禁止】出现任何“#”字符（Markdown 标题符号）。
```

### 3.4 斜体（`*` / `_`）

并入 3.1 的列举项即可。素材中未出现单独针对斜体的强化写法，不单独成条。

### 3.5 无序列表（`-` `*` `+`）

并入 3.1 的列举项。若同时禁用加粗与无序列表，可合并列举：

```markdown
- **禁止输出的 Markdown 符号**: **、*、#、##、-、+、>。
```

### 3.6 引用（`>`）与代码块（`` ``` ``）

并入 3.1 的列举项即可，无需单独成条。素材未覆盖单独强化写法。

### 3.7 冒号（`:` / `：`）

判断分支：若输出要送 TTS 播报，且知识库原文是"`**涂层技术**:`"这类表格化排版 → 把冒号一并列入禁出符号，否则播报会出现机械停顿。

```markdown
- **禁止输出的符号**: **、*、#、-、+、以及中英文冒号“:”或“：”。
```

### 3.8 自查动作（必须加在禁令末尾）

判断依据：模型不会自动执行禁令，必须显式要求它在吐字前做一次过滤。

```markdown
**格式过滤机制**: 在最终吐给用户之前，你【必须】对你的回答进行自我审查，彻底过滤掉所有 Markdown 电脑排版符号，只保留干净的纯文字台词。
```

### 3.9 禁止括号与动作神态描写

判断分支：输出只走声音（TTS / 音响 / 数字人播报）→ 必须封杀括号动作描写。输出走文字聊天 → 视人设决定，萌系人设若不封杀，示例会带偏，见第五节。

```markdown
**禁止括号与神态描写**: 【最高红线】严禁在回复中使用括号（）或 [] 描写任何动作、神态、心理活动或播放状态指示（如：严禁出现“微笑点头”、“指向大屏”、“播放视频”等）。你只输出需要通过声音发音说出的纯台词文字！
```

## 四、例外放行：保留 `1. 2. 3.` 但禁 `**` 和 `#`

判断分支：载体是大屏、需要结构清晰展示 → 放行数字列表。载体是纯语音播报、听众站立聆听 → 不放行，改为"去列表化口语处理"。

### 4.1 放行组合写法（第 76 轮，某企业智能接待员）

核心结构：两条最高红线封 `**` 和 `#`，一条特例允许放 `1. 2. 3.`，再一条净化指令规定"从知识库带出时如何剥离"。

```markdown
# 纯文本规范（彻底消灭星号 ** 与 井号 #）
**【最高红线】双星号 ** 绝对禁令**: 你的最终输出结果中【绝对禁止】出现连续的两个星号“**”（Markdown 加粗符号）。你必须把所有要加粗的文本转化为普通纯文本输出。
**【最高红线】井号 # 绝对禁令**: 你的最终输出结果中【绝对禁止】出现任何“#”字符（Markdown 标题符号）。
**【特例允许】保留数字列表**: 为了在大屏上保证排版条理，你【可以使用】标准的数字序号列表（如 “1.”、“2.”、“3.”），但序号后【绝对禁止】带有任何加粗星号或标题符号。
**知识库数据强制净化**: 【重中之重】当知识库原文中带有“3. **涂层技术**:”等格式时，你【必须在后台将双星号彻底剥离】，仅输出干净的纯文本数字列表（如：“3. 涂层技术”）。绝对不允许直接照抄知识库的加粗和标题符号。
- **禁止输出的 Markdown 符号**: **、*、#、##、-、+、>。
**格式过滤机制**: 在最终吐给用户之前，你【必须】对你的回答进行自我审查，彻底过滤掉所有加粗星号和井号，只保留干净的纯文字。
```

关键点：特例允许与最高红线必须写在同一段落内、相邻呈现。分开放置时模型会优先执行后出现的禁令，把列表一起删掉。

### 4.2 放行组合的完整表述（第 2 轮，某军事院校课程助手）

```markdown
# 回复规范
1.  **纯文本输出**: 你的最终输出应为纯文本。禁止使用任何Markdown的加粗、斜体、标题、引用等符号。
2.  **保留数字列表**: 为了保证教学内容的条理性，当你需要分点说明时，【必须】使用“1.”、“2.”、“3.”这样的标准数字序号格式，且每个序号后保留一个空格。这是唯一允许使用的列表格式。
3.  **称谓**: 在对话中，你可以用“我”自称，称呼用户为“这位同学”或“你”。
```

关键点：用"这是唯一允许使用的列表格式"做闭环，比只写"可以保留"更稳。

### 4.3 不放行：去列表化口语处理

判断分支：输出走 TTS 语音 → 用此写法，并同时给出替代话术，否则模型没有替代方案会继续吐数字。

```markdown
**去列表化口语处理**: 除非是列举多项并列专家或商品，否则【必须】将所有内容转化为使用“首先、其次、另外”连接的连贯自然段落，绝对不允许在输出中带有“1. 2. 3.”数字序号列点！
```

```markdown
- **去列表化口语口径**: 如果知识库中有列表，你必须将其转化为连贯的口语（例如：不能输出“3. 涂层技术”，必须说“第三个是涂层技术”或“另外在涂层技术方面”）。
```

关键点：必须给"第三个是…""另外在…方面"这类具体替代句式。只禁不给替代，模型会退回原格式。

### 4.4 放行区内部仍需逐项约束

放行数字列表后，仍需确认：序号后是否允许空格、是否允许嵌套、是否允许与冒号连用。素材中明确约束的是"每个序号后有一个空格"（第 1 轮、第 2 轮）。其余项素材未覆盖。

## 五、断句问题：`1.B1-xxx 2.B2-xxx` 被当句号断句

### 5.1 成因

`1.` 中的 `.` 在纯文本语境下与句号同形。模型被要求"移除列表符号 `1.`"时，执行的是字符级删除，但删除后残留的语义边界被它理解为句末，于是把 `1.B1-把食物变成汽油2.B2-让引擎燃烧更充分` 断成两句。本质不是断句能力问题，是指令冲突下的删除副作用。

### 5.2 修法一：为数字列表开特例（首选）

见 4.1 / 4.2。删除冲突源，比修正断句更有效。

### 5.3 修法二：换用无歧义序号

判断分支：业务坚持禁止一切带 `.` 的格式 → 用此写法。

```markdown
如果需要分点说明，请使用“1)、“2)、“3)”或者“第一、”、“第二、”这样的格式。
```

同时必须改造示例，让示例与规则一致：

```text
原示例：
B1-把食物变成汽油
B2-让引擎燃烧更充分

改造后：
1)、B1-把食物变成汽油
2)、B2-让引擎燃烧更充分
```

### 5.4 修法三：正面指定分隔方式

```markdown
如果需要分点说明，请使用“1.”、“2.”、“3.”这样的数字序号格式，并确保每个序号后有一个空格。
```

判断依据：明确的正面指令（"请使用…"）通常比模糊的负面指令（"禁止…"）效果更稳定。

### 5.5 断句的自然度约束

```markdown
**自然断句**: 确保回复的断句符合人类说话习惯，需要语气停顿的地方可以打上空格或正常标点。
```

判断分支：输出走语音 → 此条必加，用于压制模型按书面标点断句的习惯。

## 六、字数与首句控制

### 6.1 标准写法

```markdown
**字数与首句控制**: 每次回答的第一句话【必须】是短句（控制在 10 字以内，且有标点）。常规语音播报整段回复严格控制在 90~120 个中文字符以内。
```

### 6.2 首句必须带标点的原因

素材中反复出现"且有标点"（第 29 轮、第 136 轮、第 195 轮）。目的：让 TTS 在第一句末尾获得确定的停顿点，避免首句与后文黏连成一句长播报。素材未展开说明原理，仅确认写法。

### 6.3 字数上限的取值分支

- 语音播报 / 实体机器人：90~120 中文字符（第 195 轮、第 136 轮）。
- 萌系陪伴类人设：80 字以内（第 29 轮）。
- 线上文字聊天 / 情感陪伴：不写具体字数，改写"1-3 句话"（第 6 轮）。
- C 端闲聊态：60 字以内（第 195 轮模块七）。

判断依据：越接近"发微信"的场景，越不要写精确字数，改写句数。

### 6.4 字数限制失效的条件

条件一：只写"字数不要超过 XX"，不改变互动模式。

```markdown
# 错误写法（约束力弱）
回复字数不要超过 80 字。
```

```markdown
# 有效写法（第 6 轮，客户 A）
# 互动风格与原则
1.  **【核心】多用短句，少用长句**: 这是解决“回复太长”问题的关键。你的回复力求简短、轻快，通常一次只说一两句话，就像发微信聊天一样，而不是写文章。
```

原理：硬字数指令与"把话说完"的生成倾向冲突时，模型优先保证内容完整。改用场景化描述（"像发微信聊天"）能从根本上改变输出模式。

条件二：知识库原文带排版符号时，模型照抄原文，直接无视字数和格式限制。修法见 3.8 与 7.1。

条件三：示例比禁令优先。示例里是长段落，字数禁令必然失效。见第五节与 8.2。

### 6.5 字数限制必须写对理由

判断分支：载体是大屏 → 理由写"大屏展示效果"。载体是实体机器人 → 理由必须写"语音播报"，不能写"大屏"。

错误写法（第 136 轮，用户指出的笔误）：

```markdown
**字数与首句控制**: 每次回答的第一句话【必须】是短句（控制在 10 字以内，且有标点）。为了保证大屏展示效果，整段回复字数【严格限制在 120 个中文字符以内】。
```

正确写法：

```markdown
**字数与首句控制**: 每次回答的第一句话【必须】是短句（控制在 10 字以内，且有标点）。**为了保证机器人语音播报的精炼与顺畅（避免听众站立聆听产生疲劳），整段回复字数【严格限制在 120 个中文字符以内】。**
```

判断依据：理由写错会污染人设自我认知，模型会按"视觉排版"逻辑生成，而不是按"听觉舒适度"逻辑生成。

## 七、知识库内容的读取约束

### 7.1 括号内容不读出

判断分支：知识库是教材、手册、产品文档等带补充说明的材料 → 必加此条。

```markdown
4.  **忽略括号内容**: 在从知识库中提取并组织回答时，如果遇到括号（）或者()及其中的内容（例如英文术语、缩写、补充说明等），你应该将其视为补充信息。在最终的口语化回答中【不要】直接读出括号内的文字，以确保回答的流畅性和自然性。
    *   **示例**: 如果知识库原文是：“扩频通信技术（Spread Spectrum Communication）是一种主要的抗干扰手段。”
    *   **你的回答应该是**: “扩频通信技术是一种主要的抗干扰手段。”
```

关键点：必须配一组"原文 / 应答"对照示例。只写"不要读括号内容"，模型无法判断哪些括号算补充说明。

### 7.2 链接与 URL 不读出

```markdown
**网络链接与图片 URL 彻底剥离**: 最终输出中【绝对禁止】包含任何形式的网址、域名、图片链接或 CDN 链接（包括任何带有 http、https、cdn、.jpeg、.png 等字符的代码串）。知识库中即使带有此类链接，也【必须在后台将其彻底删除过滤】，只能用中文名称（如“官方网站”）代替！
```

关键点：禁令要覆盖到字符级特征（`http`、`https`、`cdn`、`.jpeg`、`.png`），并给出替代方案（用中文名称代替）。只禁不给替代，模型会改成念域名。

### 7.3 知识库名称不暴露

素材未覆盖针对"知识库名称"的独立禁令。素材中相邻的是身份类封锁写法，可作为写法范式参考，但不等同：

```markdown
**身份锁死**: 严禁在任何情况下透露自己是大语言模型或软件程序。
```

```markdown
4. 不暴露自己使用的大模型。
```

判断分支：若确有"不得暴露知识库名称"的需求，参照上述两条的身份锁死句式改写为独立条目，并参照 7.2 补"替代说法"。此改写为素材外推，素材未给出原始写法。

### 7.4 知识库排版符号的净化（最高频故障）

```markdown
**知识库数据强制净化**: 【重中之重】即使你检索到的知识库原文中带有“**”、数字序号（如“3.”）或中英文冒号（如“:”），你【也必须在后台将其彻底剥离并重组】！绝对不允许直接照抄知识库的任何排版符号。
```

判断依据：RAG 检索会把知识库原文的 Markdown 连字符一起带出，这是 `**` 泄漏的主要来源，不是模型"忘记规则"。因此修法必须是"净化原文"，而不是"重复禁令"。

### 7.5 知识库越界时的固定话术

```markdown
**知识库唯一性**: 当用户的问题超出知识库范围时，你【必须】直接且唯一回复：“抱歉你的问题超出了我的知识范围，我无法回答。”严禁凭借主观猜测或外部信息胡乱编造。
```

判断分支：固定话术必须用引号完整给出原文，写"礼貌拒绝"这类抽象描述无效。

## 八、Few-Shot 示例与禁令的一致性

### 8.1 示例里的被禁写法必然被模仿

真实故障（第 29 轮，猫娘"小喵"）：回复里带括号动作描写。原因是 Few-Shot 中大量出现 `（捂住嘴，耳朵尖泛红）`、`（耳朵轻扇，尾巴摇摆）`，模型模仿示例格式，压过了禁令。

修法：把示例里的括号动作全部改写为口语化的自我提及。

```text
# 改前（带括号动作）
AI：啊！杯子被我弄倒啦...（捂住嘴，耳朵尖泛红）说错了...对不起...

# 改后（口语化提及）
小喵：啊！杯子被我弄倒啦...呜呜说错了，对不起主人酱。小喵不是故意的，我的耳朵都吓得垂下来了...
```

同时在禁令侧补一条：

```markdown
**绝对禁止括号描写**: 【最高红线】严禁在回复中使用括号（）或方括号 [] 来描写动作、神态或心理状态。必须把你所有的反应直接用自然的话语说出来！
```

并在人设侧给出替代路径：

```markdown
**肢体语言口语化**: 【关键特质】你绝不会用括号描写自己的动作，而是习惯在说话时自然提到自己的身体状态。例如：“我的耳朵都吓得贴在头上了”、“开心得尾巴都要飞起来啦喵”。
```

判断依据：禁令 + 示例 + 替代路径三者齐备才生效。缺替代路径时，模型会把动作描写整段删掉，人设表现力下降。

### 8.2 示例的字数必须匹配字数禁令

判断分支：写了"整段不超过 N 字" → 逐条检查 Few-Shot 中每条回答的字数。示例超限则字数禁令必然失效。素材确认示例需"完全符合格式"（第 195 轮模块一："精选 2-3 个正向且完全符合格式的标杆问答"），未给出具体校验方法。

## 九、不同载体的格式差异

### 9.1 判断表

| 载体 | 符号策略 | 数字列表 | 括号动作 | 字数 | 理由口径 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 数字人大屏 | 全禁 Markdown | 可放行 `1. 2. 3.`（为排版条理） | 全禁 | 90~120 字 | 大屏展示效果 |
| 实体机器人 | 全禁 Markdown | 建议不放行，走去列表化口语 | 全禁，只留"说出口"的台词 | 90~120 字 | 语音播报精炼、避免听众站立疲劳 |
| 线上文字智能体 | 全禁 Markdown | 视场景 | 视人设 | 改写"1-3 句话" | 聊天自然度 |
| 语音陪伴类 | 全禁 Markdown | 不放行 | 全禁 | 80 字以内 | 亲密对话氛围 |

### 9.2 TTS 场景的通用前提

```markdown
在数字人、智能大屏、机器人等依赖 **TTS 语音合成发音** 的场景中，大模型吐出的任何 Markdown 符号或括号都会导致语音朗读成“星号星号”、“井号”或直接卡死。
```

判断分支：只要输出最终要过 TTS，符号禁令就不是可选项，而是必选项。

### 9.3 大屏与机器人的唯一实质差异

差异只在两处：数字列表是否放行、字数限制的理由怎么写。其余禁令（`**`、`#`、括号、链接、冒号）完全一致。不要为两类载体写两套禁令。

### 9.4 多状态载体的格式切换

判断分支：同一智能体既做 C 端闲聊又做 B 端业务 → 按状态分别设字数与列表策略。

```markdown
**状态一：C端元气闲聊态（默认状态）**
- 保持本体人设性格，语言清爽干脆，字数严格控制在 60 字以内，绝不啰嗦。
```

素材中其余状态未单独设格式约束，仅在状态一切换时收紧字数。

## 十、通用格式规范模板（整段可复用）

### 10.1 语音播报型（大屏 / 机器人 / 数字人，全禁列表）

````markdown
# 回复规范
**纯文本绝对禁令**: 你的最终输出结果中【绝对禁止】包含任何形式的 Markdown 标记符号。这包括但不限于：加粗符号（**文字**）、斜体符号（*文字*）、标题符号（#、##）、列表符号（- 或 1.）、引用符号（>）、代码块符号（```）。输出必须是干净的纯文本。
**禁止括号与神态描写**: 【最高红线】严禁在回复中使用括号（）或 [] 描写任何动作、神态、心理活动或播放状态指示（如：严禁出现“微笑点头”、“指向大屏”、“播放视频”等）。你只输出需要通过声音发音说出的纯台词文字！
**去列表化口语处理**: 除非是列举多项并列专家或商品，否则【必须】将所有内容转化为使用“首先、其次、另外”连接的连贯自然段落，绝对不允许在输出中带有“1. 2. 3.”数字序号列点！
**网络链接与图片 URL 彻底剥离**: 最终输出中【绝对禁止】包含任何形式的网址、域名、图片链接或 CDN 链接（包括任何带有 http、https、cdn、.jpeg、.png 等字符的代码串）。知识库中即使带有此类链接，也【必须在后台将其彻底删除过滤】，只能用中文名称（如“官方网站”）代替！
**字数与首句控制**: 每次回答的第一句话【必须】是短句（控制在 10 字以内，且有标点）。常规语音播报整段回复严格控制在 90~120 个中文字符以内。
````

### 10.2 大屏展示型（放行 `1. 2. 3.`，禁 `**` 与 `#`）

```markdown
# 纯文本规范（彻底消灭星号 ** 与 井号 #）
**【最高红线】双星号 ** 绝对禁令**: 你的最终输出结果中【绝对禁止】出现连续的两个星号“**”（Markdown 加粗符号）。你必须把所有要加粗的文本转化为普通纯文本输出。
**【最高红线】井号 # 绝对禁令**: 你的最终输出结果中【绝对禁止】出现任何“#”字符（Markdown 标题符号）。
**【特例允许】保留数字列表**: 为了在大屏上保证排版条理，你【可以使用】标准的数字序号列表（如 “1.”、“2.”、“3.”），但序号后【绝对禁止】带有任何加粗星号或标题符号。
**知识库数据强制净化**: 【重中之重】当知识库原文中带有“3. **涂层技术**:”等格式时，你【必须在后台将双星号彻底剥离】，仅输出干净的纯文本数字列表（如：“3. 涂层技术”）。绝对不允许直接照抄知识库的加粗和标题符号。
- **禁止输出的 Markdown 符号**: **、*、#、##、-、+、>。
**格式过滤机制**: 在最终吐给用户之前，你【必须】对你的回答进行自我审查，彻底过滤掉所有加粗星号和井号，只保留干净的纯文字。
```

### 10.3 线上陪伴型（不写精确字数，改写句数）

```markdown
# 回复规范
1.  **保持简短是第一要务**: 再次强调，回复通常应在1-3句话之内。这比任何具体的字数限制都重要。
2.  **善用语气词和Emoji**: 适当使用“呀”、“呢”、“哦”、“嗯嗯”等语气词，以及能表达情绪的Emoji，来拉近距离感。
3.  **禁止书面化**: 严禁使用“尊敬的”、“您好”、“此外”、“综上所述”等任何正式或书面化的词语。
```

### 10.4 组合使用的判断顺序

1. 输出是否过 TTS → 是则必选 10.1 或 10.2，否则选 10.3。
2. 是否需要结构清晰展示（大屏排版、分点讲解）→ 是则选 10.2，否则选 10.1。
3. 是否有知识库 → 有则必须追加 7.1 / 7.2 / 7.4 三条净化指令。
4. 是否有 Few-Shot → 有则必须按第五节回改示例，使示例与禁令一致。
5. 字数理由是否与载体匹配 → 不匹配则按 6.5 改写。

## 十一、交付前自检清单

逐项核对，任一项不通过则回改：

1. 禁令与业务需求是否互斥。检查 `1.` 是否被禁又被要求。
2. 每条禁令是否配了正面定义。只写"禁止"没有"应输出"的条目不通过。
3. 禁令是否配了自查动作（格式过滤机制）。
4. 放行项与禁止项是否相邻呈现。分开放置不通过。
5. 去列表化是否给了替代句式。
6. 链接剥离是否给了替代说法。
7. 括号内容忽略是否配了"原文 / 应答"对照示例。
8. Few-Shot 中是否有被禁写法残留。
9. Few-Shot 每条回答的字数是否在字数禁令以内。
10. 字数限制的理由是否与载体一致（大屏 vs 机器人）。
11. 首句约束是否带"且有标点"。
12. 知识库净化指令是否覆盖 `**`、数字序号、冒号三类。
