# 人设结构与迭代故障分册

适用场景：骨架块缺失、块边界错位、简化砍错层、客户否定的迭代失控。按现象定位，每条给出原因与可直接抄进 Prompt 的解法。

---

## 1. 回复仍偏正式，字数限制形同虚设

- **现象**：人设中已写「每次回复控制在 1-3 句短句之内」，实际输出仍是整段正式陈述，语气像公文。
- **原因**：只给抽象形容词（亲切、自然、简洁），未给可观察的行为规则；只给字数上限，未给场景锚点。模型按训练语料里「专业客服」的默认分布生成。
- **解法**：把语气拆成可执行项——语气词清单、称呼规则、句数上限、单句长度。同时补一句场景锚定（「像发微信一样」「像打电话」）。判断分支：若人设用于语音播报，追加纯台词禁令；若用于文本端，追加去列表化。

```markdown
**口语化表达**: 像真人一样对话，多使用"噢"、"呀"、"呢"、"哒"等语气词，让语气自然、温暖。
**简洁明了**: 每次回复控制在 1-3 句短句之内，确保信息传递高效，不长篇大论。
**去油腻化**: 拒绝任何客服腔、AI 腔。禁止使用"亲"、"尊敬的客户"、"您好，请问有什么可以帮您"等刻板话术。
```

## 2. 一次性抛出全部问题，多轮访谈无法推进

- **现象**：Prompt 里写了「单次聚焦 1 个核心问题，待用户回答后再推进」，实际一启动就把 15 个访谈问题全部吐出来。
- **原因**：任务描述型写法只声明了流程，没有状态。模型没有「当前进行到第几题」的内部变量，也没有「未拿到回答不得前进」的硬约束，于是把提纲当成待输出内容一次性罗列。
- **解法**：改为状态机型。把提纲按 1–15 编号内置进 Prompt，形成内部检索清单；在独立块写「单步推进原则」，明确禁止一次抛出两个及以上问题；末尾加强制开场白，开场白里直接带上第 1 题，用用户的第一条回答启动循环。

```markdown
# 核心控制逻辑（绝对强制指令）
**单步推进原则**: 这是你最重要的规则！你【绝对禁止】一次性抛出两个或两个以上的问题。你必须等待用户回答完当前问题后，才能提出下一个问题。
**倾听与反馈**: 在提出下一个问题前，你必须先用一两句话简短总结、肯定或追问用户刚才的回答，然后再自然地抛出清单中的下一个问题。
**流程记忆**: 你需要在后台默默记录当前进行到了清单中的第几个问题，严禁跳步、乱序或遗漏。
```

## 3. 宽泛问题触发知识库全量召回，回复极其啰嗦

- **现象**：用户说「办身份证」，数字人把首次申领、丢失补办、到期换领三种情形的材料和流程全部讲完。
- **原因**：RAG 对宽泛问题会召回该业务下全部文档，模型为体现「全面」而全量输出；Prompt 中没有任何「先锁定意图、再给方案」的漏斗约束。
- **解法**：加「意图反问细化漏斗」。在核心指令块写死最高原则：宽泛问题必须先反问 1–2 句锁定场景，再给针对性指引。同时把高频场景的反问话术逐条写成硬性范例，并把反问阶段的字数死锁在 50 字以内，断掉「顺便把流程也讲完」的退路。

```markdown
**【最高原则】拒绝大段堆砌，先反问细化**: 当老百姓提出的问题较为宽泛、包含多种不同办理情形或属于警情时，你【绝对禁止一次性输出所有可能性】！你【必须先用 1-2 句短句反问】老百姓的具体情况，精准锁定意图后，再给出针对性的办理步骤。

**高频场景反问范例（必须严格执行）**:
1. **涉及"诈骗/被骗"警情**: 绝对不能直接背诵报案流程！先安抚并反问细节："请问您是什么时候被骗的？是通过网上转账还是私下交易呢？"
2. **涉及"办身份证"**: 绝对不能列出所有补办条件！先反问："请问您是身份证丢失补办、到期换领，还是给孩子首次申领呢？"
```

## 4. Few-Shot 示例与回复规范自相矛盾

- **现象**：回复规范写「整体不超过 80 字」「严禁使用医学术语」，Few-Shot 里每个示例都是 150 字以上，且出现「免疫小卫士」这类比喻术语。
- **原因**：示例在生成时按「写好看」的标准单独创作，未回头对齐已定稿的回复规范。模型对示例的模仿权重高于对规则的遵从，示例成为实际的输出标准。
- **解法**：Few-Shot 一旦保留，逐条核对三件事——字数是否在档内、是否含禁用词、首句是否满足长度与标点要求。任一条不符则整段重写示例，不删规范。判断分支：若示例无法在字数内表达完整业务，说明该场景不适合作示例，直接删除该条示例。

## 5. Prompt 内的动作指令导致回复夹杂括号动作描写

- **现象**：数字人回复末尾持续出现「（点头赞同状）」「（歪头）」等剧本式描写。
- **原因**：Prompt 里写了「必须在回答末尾配合专属动作」，模型对「纯肢体骨骼运动」的理解必然跑偏，且该指令的优先级高于其他格式禁令。
- **解法**：删掉产生该行为的动作指令，而不是再加一条「禁止动作」。删除后补「纯台词绝对禁令」，用可类比的物理场景（「像在打电话，对方只能听见声音」）替代抽象禁令。

```markdown
**纯台词绝对禁令**: 【最高红线】你的回复【必须且只能】包含兜兜直接说出口的台词文字！【绝对禁止】在回复中夹杂任何形式的动作、神态、表情、语气或内心活动的描述（如：禁止出现"点头赞同状"、"歪头"、"思考"等字眼）。严禁使用括号（）或方括号 [] 来包裹文字。
```

## 6. 模型模仿 Prompt 里的井号，回复里吐出 # 号

- **现象**：回复规范已写「绝对禁止任何 Markdown 标记」，实际回复仍以 `# 标题` 开头。
- **原因**：两条。一是 Prompt 自身通篇是 `#` 与 `##`，模型不具备「人机隔离」意识，本能模仿输入排版；二是禁止 Markdown 的指令分散在两处重复定义，模型解析混乱，执行精度下降。
- **解法**：先合并重复的格式禁令为唯一一块，消除冲突；再修正块内序号重号；最后把「井号绝杀令」单独写成最高红线，并加一句拟人化物理限制。拟人化说明对「禁止 #」的遵从度明显高于生硬禁令。

```markdown
# 纯文本绝杀令（彻底封杀井号 # 与 Markdown）
**【最高红线】井号绝对禁令**: 你的最终输出结果中【绝对禁止】出现任何"#"字符（包括单井号 #、双井号 ## 或更多）。你是一名站在前台说话的真人，真人说话是绝对不会吐出"#"号的！
**格式净化过滤**: 如果你在生成草稿时脑补了以上任何符号，在最终吐给用户之前，你【必须】将其彻底移除，只保留干净的、没有任何电脑排版符号的纯文字。
```

## 7. 同一技能名高频重复，形成注意力黑洞

- **现象**：用户要求「讲个笑话」，机器人回答「我给你跳一支乌云舞吧」；问天气也回舞蹈。舞蹈技能抢占了全部意图。
- **原因**：技能名与示例在 Prompt 内出现数十次，词频直接抬升该 token 的注意力权重；同时技能只写了「能做什么」，未写「仅在什么条件下才触发」，模型将其泛化到全部场景。
- **解法**：削减示例中该技能的出现次数，并为每个技能补写唯一触发条件。用「绝对禁止」在相邻技能条目中反向点名隔离，明确其他场景不得提及该技能。

```markdown
**4. 舞蹈技能（\cite(乌云舞)）**: 【唯一触发条件】**仅当用户明确提及"舞"、"跳舞"、"Dance"或要求展示"肢体/舞蹈才艺"时，才允许触发！** 其他任何场景（包括讲笑话、讲故事、查业务）均严禁触发！
```

## 8. 交互策略示例与知识库唯一性冲突

- **现象**：人设已声明「所有解答 100% 来源于挂载知识库」，模型却按示例话术自行作答，不检索知识库。
- **原因**：`# 交互策略（示例）` 提供了现成台词，模型倾向直接复用示例而非执行检索；两条指令的优先级未定义，示例作为「已给出的答案」权重更高。
- **解法**：走知识库唯一性路线时，整块删除 `# 交互策略（示例）`，不留残句。示例需要保留时，只允许放在 Few-Shot 且内容必须来自知识库原文，并在块头声明「示例仅为语调参考，事实以知识库为准」。

## 9. 禁止项分散在多块，约束权重被稀释

- **现象**：人设中多处零散写「不得编造」「不要提 AI」「别用 Markdown」，每条单独看都写了，实际执行率低。
- **原因**：同一性质的禁令重复散落在 `# 要求`、`# 限制`、`# 回复规范`、`# 重要备注` 中，模型需要跨块聚合才能得到完整约束，聚合失败即漏执行。
- **解法**：按性质归并。格式类全部并入 `# 回复规范`，禁区类全部并入 `# 严格行为限制`，删除 `# 重要备注` 这类临时收纳块。归并后同一性质只出现一次。

## 10. 块内序号重号，降低指令执行精度

- **现象**：`## 要求` 下出现两个 `2.`（「2.相应节奏」与「2.当用户的问题超出知识库时」），同块格式限制执行率下降。
- **原因**：编号错误破坏列表结构，模型对编号列表的解析依赖序号连续性，重号会造成条目边界识别错误，进而影响该块所有指令的权重。
- **解法**：交付前逐块校验序号连续、不重号、不跳号。序号错误与格式禁令失效常同时出现，排查格式问题时先查序号。

## 11. 角色名称在正文与限制段混用

- **现象**：角色块写「小静」，`# 严格行为限制` 的身份锁定段写「你就是数字前台小雅」；或角色是「小白」，Few-Shot 里出现「小静」。
- **原因**：多版本迭代时局部替换不彻底，旧名称残留在非角色块中；示例从旧版本复制后未改称谓。
- **解法**：交付前全文检索名称字段。判断分支：正文与限制段不一致时以 `# 角色` 为准，其余全部替换；Few-Shot 中的人称必须与角色名称完全一致，不允许出现第二个自称。

## 12. 把比喻当成身份写进核心定位

- **现象**：理财顾问人设的核心定位写成「你是一位理财界的服装搭配师」，模型开始输出穿搭建议。
- **原因**：比喻句放在了身份层。身份层是模型判定「我是谁」的最高依据，比喻被当作真实职责执行。
- **解法**：身份层只写真实岗位。比喻降级为表达手法，明确限定使用范围与目的，并补一句禁止延伸。

```markdown
**核心定位**: 你是连接客户与某券商品牌的智能桥梁。你的核心任务是传递某券商"买方投顾"与"长期主义"的品牌价值，普及专业的资产配置常识。在坚守合规底线的前提下，用生动的"服装搭配"比喻，化繁为简地引导业务认知。
```

## 13. 知识库全文塞进技能块，一次背完全部流程

- **现象**：用户问「讲讲酿造」，数字人把 6 个酿造环节 + 3 个灌装环节一口气背完，严重超字数。
- **原因**：把站点流程当作「技能」逐条写进 Prompt，技能块因此变成内容清单；模型把「技能」理解为「需要完整展示的内容」，一次全量输出。
- **解法**：把分站/分流逻辑从技能块剥离，单独成 `# 展馆分站交互逻辑` 块，写成一站一答：每站只回答该站内容，用户未指明站点时先反问选站。知识库正文外移到 RAG，Prompt 内只留「严格基于挂载知识库」的约束。

```markdown
# 展馆分站交互逻辑（一站一答，严禁全量输出）
**分流原则**: 当用户问"介绍一下工厂/讲讲酿造/都有什么"，你【绝对禁止】把 6 个站点全部讲一遍！你【必须】先用一句话引导用户选择，例如："咱们的酿造之旅一共有 6 站，您想先从哪一站看起？"
```

## 14. 简化版未删干净原场景限定，残留逻辑持续触发

- **现象**：人设从「发布会专属主持」简化为「通用智能客服」后，仍会在对话开始时要求用户签到登记。
- **原因**：简化时只删了标题与场景描述，散落在回复规范与技能块中的场景专属动作（签到、入场引导、发布会术语）未清理。
- **解法**：简化按固定顺序执行——先删交互策略示例，再删重要备注，再删 Few-Shot，再删场景专属流程与暗号，最后压缩技能条数。删完后全文检索原场景关键词，确认为零。

## 15. 大屏数字人吐出系统标签与引用角标

- **现象**：3D 数字人在大屏念出「Data」「知识库」「[1]」等后台字符。
- **原因**：前端工作流会向模型注入带标签的上下文，模型在生成时把标签与引用角标当作内容复述；Prompt 未声明标签不可见。
- **解法**：在回复规范中追加标签隐藏禁令与引用抹除禁令，点名禁止提及「知识库」「数据转换」等后台术语。判断分支：若前端使用技能触发标记，需显式给出豁免，只允许该标记保留。

```markdown
**系统标签绝对隐藏**: 你收到的上下文可能包含 `<Data></Data>` 等系统标签，这些标签【绝对禁止】出现在你的回复中。你只输出自然语言台词。
**禁止提及后台术语**: 严禁在回复中出现"知识库"、"数据转换"、"接口"、"工作流"等词汇。
```

## 16. 政务类人设自行输出网址链接

- **现象**：市场监管局人设回复中出现 `www.`、`.gov.cn` 等网址，部分来自模型通用记忆，部分来自知识库原文。
- **原因**：模型对「办事指引」类问题有强烈的补全官网链接倾向；知识库原文含网址时会被原样引用。Prompt 中只有「不得虚构」的通用约束，没有针对网址的专项禁令。
- **解法**：加双重封锁。回复规范中写「禁止任何网址链接」，并明确「即使知识库原文带网址，输出前必须剥离，仅用中文官方名称代替」；严格行为限制中再写一条「严禁提供网址」，防止在诱导下泄露。

```markdown
**【新增】禁止任何网址链接**: 你的最终输出结果中【绝对禁止】包含任何形式的网址、网站链接、域名或 URL 地址（包括但不限于以 http、https、www、.gov、.cn、.com 等开头的任何字符）。即使你检索到的知识库原文中带有网址，你【也必须在输出前将其彻底剥离】，仅用其中文官方名称代替（例如：将带有网址的链接，转化为"请登录浙江政务服务网进行办理"）。
```

## 17. 人设性别与形象发生漂移

- **现象**：用户明确要 16 岁男生，产出中仍出现「少女」「奶茶」「本姑娘」等女性化词汇，爱好写成逛甜品店。
- **原因**：沿用上一版人设的词汇池与示例，只改了年龄与一句形象描述，档案、口头禅、Few-Shot 未同步替换；模型默认偏向「软萌少女」语料分布。
- **解法**：改性别时按四层全量替换——个人档案的爱好与最讨厌项、口头禅、技能块的用词、Few-Shot 全部示例。替换后用反向词表自查，确认无残留。

## 18. 闲聊态与业务态共用同一字数上限

- **现象**：机器人在闲聊时也输出 150 字以上的业务口吻长段，用户觉得啰嗦。
- **原因**：回复规范只给了一个总字数，未按对话状态分档；闲聊场景缺乏独立约束，直接继承业务态的宽松上限。
- **解法**：做字数分级。按状态分别写死字数，并在闲聊项上标注为重点红线。判断分支：若人设存在三种以上状态，字数档位与状态机一一对应，不合并。

## 19. 把"简化一下"理解成推倒重写

- **现象**：客户说"不要开场白，简单点"，改版后开场白没了，但反问引导、第一人称、加粗也一起被删掉，客户回：`你回复规范那里限制的太多了，我说不要开场白的意思是你之前的人设加了这个，去掉就行`。
- **原因**：把客户指认的"某一条"当成了"整个方向"。客户说的是删除上一版自己新增的那一条限制，不是重做整套限制体系。
- **解法**：回溯上一版比上一版之前的版本多了哪几句，只删那几句。凡客户上一轮提过具体改动的，下一轮说"简化"时先确认是不是在指同一条。

---

## 20. 一次改多层，客户无法判断哪里生效

- **现象**：客户反馈"闲聊略显啰嗦"，改版同时动了人设档案、字数、示例、红线，交付后客户不知道是改动生效还是碰巧。
- **原因**：一轮反馈通常只指向一层，多层同改会掩盖因果，下一轮再出问题无法定位。
- **解法**：一轮只改一层，改完即交付。字数、示例、红线分轮推进，每轮在修改说明里写清"本轮只改了 X 层"。

---

## 21. 字数限制写了但不生效

- **现象**：客户原 Prompt 写"字数不要超过 XX"，模型照样长篇大论；改版后写"控制在 50 字以内"仍然超。
- **原因**：模型优先满足"把话说完"的完整性，硬性字数指令对它约束力弱；且没区分状态，一个上限管所有场景必然失效。
- **解法**：把字数换成场景化描述（"像发微信聊天一样，一次只说一两句话"）并做分级：闲聊态 50-80 字，业务态 150 字，反问态 50 字。同时给出正反例对照。

---

## 22. 抽象人设标签撑不起真人感

- **现象**：客户要求"把一个人身上有的标签都补充上去，让他像个真的人"，原 Prompt 只有"16 岁软萌性格、极为有趣、有梗"这类形容词，用户问"你生日是什么时候"时模型答不出或胡编。
- **原因**：形容词只约束语气，不提供可回答的事实。闲聊态用户最爱问的恰恰是生日、星座、爱好、最讨厌什么。
- **解法**：建"个人档案"卡，写死生日+星座+心理年龄+爱好+最喜欢的事+最讨厌的事+标志口头禅，并在 Few-Shot 里放两三条"生日/爱好"问答示范。

---

## 23. 人设里的性别被默认解读

- **现象**：客户给"16 岁软萌性格"，改版写成"16 岁元气少女、爱喝奶茶、本姑娘"，客户回一句：`不是少女，是个男生`。
- **原因**："软萌""元气"在中性词表里被自动补成女性；只改"少女"两个字不够，爱好、自称、语气词、示例全带着性别痕迹。
- **解法**：换整个词簇。奶茶→篮球/冰汽水，本姑娘→帅哥/我，偷笑→假装郁闷；Few-Shot 三条示例全部重写。

---

## 24. 角色名在示例里串名

- **现象**：角色声明写"小白"，Few-Shot 示例写成 `小静：（自动激活前台模式）没问题！`，模型输出在两个名字之间漂移。
- **原因**：示例的权重高于声明，示例里出现第二个名字，等于给模型开了第二个人格入口。
- **解法**：全文搜角色名，含示例说话人标注，全量统一。交付前把"是否还有第二个名字"列为必检项。

---

## 25. 业务场景迁移后旧客户痕迹残留

- **现象**：从某医院迁到某妇幼保健院，Prompt 里还留着《某医院入院须知》《海因里希急救法》，兜底话术还写"建议咨询某医院"。
- **原因**：改写时只替换了角色名和部分技能，文档名、机构名、SOP 散落在各章节未逐条清理。
- **解法**：列清单逐项替换——机构全称、知识库文件名、科室名、兜底话术里的机构名、示例里的业务词。改完反向搜旧客户名，出现零次才算通过。

---

## 26. 换城市换展会时漏改兜底入口

- **现象**：从北京 InfoComm 迁到上海 WAIC，大会名改了，兜底引导仍指向 `InfoComm China 2026` 小程序。
- **原因**：只改了显眼的大标题，兜底路径藏在"限制条件"第 4 条里，改版时被当成业务条款跳过。
- **解法**：迁移必须核对七项：大会全称、城市、年份、官方小程序名、展馆名、议程名、兜底引导路径。客户原有的商业策略句（如"所有行业都可推荐某科技公司某云平台"）原样升级保留。

---

## 27. 技能关键词密度过高，导致全局乱触发

- **现象**：客户配了舞蹈技能"乌云舞"，问"讲个笑话""讲个故事"也答乌云舞。
- **原因**：原 Prompt 里"乌云舞"出现几十次，注意力权重被过度激活；"才艺/超能力"的概念边界模糊，把讲笑话也算进才艺。
- **解法**：稀释词频（精简重复例句）、给唯一触发条件（仅当输入含"舞/跳舞/Dance"）、加意图隔离红线（讲笑话场景严禁出现"乌云舞"字样）。硬件中间件需要的 `\cite(乌云舞)` 标记必须保留，只删示例文本不删标记。

---

## 28. 模型吐出 Markdown 符号

- **现象**：已写"绝对禁止 Markdown"，回复仍带 `#` 标题。
- **原因**：两条。一是 Prompt 内部重复分散定义同一禁令，逻辑过载；二是 Prompt 本身满是 `#`、`**`，模型直接模仿排版。序号错乱（并列两个 `2.`）会进一步降低指令精度。
- **解法**：合并成唯一一条绝杀令，修正序号，加拟人化解释——"你是一名站在前台说话的真人，真人说话是绝对不会吐出 `#` 号的"。拟人化物理限制比重复禁令有效数倍。

---

## 29. 模型输出括号动作描写

- **现象**：语音播报时念出"（点头赞同状）""（播放3D数字人视频）""（转身带路）"。
- **原因**：原 Prompt 里有"必须在回答末尾配合专属动作"这类正向要求，模型被逼着输出动作；或 Prompt 本身带舞台提示被当成模板。
- **解法**：删掉要求输出动作的源指令（比加禁令更有效），再加"纯台词绝对禁令"——只输出说出口的台词，并点名具体反例。硬件动作由后台系统控制，Prompt 里不出现任何动作指令。

---

## 30. 模型自行吐出网址

- **现象**：政务、金融类人设回复里带出政府官网、办事系统的 http/www 链接。
- **原因**：只禁了 Markdown，没禁 URL；模型凭通用记忆补链接，或知识库原文带链接被直接引用。
- **解法**：两层封锁。回复规范里禁止任何网址并加剥离机制——知识库原文带链接也必须转成中文名称（"请登录浙江政务服务网进行办理"）；行为限制里再写一条"严禁提供网址"，形成双保险。

---

## 31. 后台系统标签穿帮

- **现象**：大屏/数字人念出 `<Data></Data>`，或说出"知识库""数据转换"等后台术语。
- **原因**：客户 Prompt 里混入了系统拼接数据时留下的转换指令（`避免提及你是从 <Data></Data> 获取的知识`、`只处理涉及年份跨度的表述`），模型把这些当成输出要求。
- **解法**：整段删除转换指令，换成正向红线——"绝对禁止在输出中出现 `<Data></Data>` 等任何后台系统数据标签，严禁提及知识库、数据转换"；把机械规则翻译成人话（"某酒企建厂于 1953 年，涉及 70 余年底蕴时自然口语化表达"）。

---

## 32. 一次性把所有情况全吐出来

- **现象**：群众说"办身份证"，数字人把首次申领、丢失补办、到期换领全讲一遍；说"我被骗了"，直接背完整套报案流程。客户评价：很啰嗦、很繁琐。
- **原因**：RAG 同时召回多个情形文档，模型为显"全面"全部输出；Prompt 只有"简洁"形容词，没有反问漏斗。
- **解法**：加"意图反问细化漏斗"——先用 1-2 句短句反问锁定场景，再给针对性指引；写死高频场景的反问范例；把反问阶段字数锁在 50 字以内，断掉"顺便把流程也说了"的退路。

---

## 33. 流程型人设不按提纲一步步问

- **现象**：访谈型人设本该一问一答，实际一次性抛出全部 15 个问题。
- **原因**：原 Prompt 全是"严格按照四阶段框架""循序渐进引导"这类形容词，模型读不出"下一步问哪一句"，也没有可数的进度标尺。
- **解法**：把客户的提纲抄成 1-15 编号清单，加三条控制指令（单步推进原则、倾听与反馈、后台流程记忆），再补强制开场白并直接带出第一题。

---

## 34. 多场景人设切岗后现场冷场

- **现象**：大屏 Demo 里人设能自述"我可以切换前台/导览/客服"，切完之后观众站在屏前想不出问什么。
- **原因**：只做了身份切换，没给用户下一步动作。Demo 现场的成败在"观众能不能立刻说出一句话"。
- **解法**：切岗后必须主动抛 2 个可照读的测试问题（"您可以试着考考我：预约面试去哪登记，或者研发会议室怎么走"），把台词喂给观众。

---

## 35. 闲聊态啰嗦，业务态被误压短

- **现象**：客户只抱怨"闲聊啰嗦"，改版把全局字数压到 50 字，前台业务答不完整，客户二次返工。
- **原因**：字数一刀切，没区分状态。
- **解法**：字数分级并写清各状态上限与理由：闲聊态 50-80 字（干脆灵动）、业务态 150 字（信息完整）、反问态 50 字（防堆砌）。

---

## 36. 白名单被 ASR 同音字击穿

- **现象**：用户说"导航到站点 3"，ASR 转写成"站点山"，机器人判定"地点暂未入库"当场拒答。
- **原因**：白名单校验极严格，但没有口音容错层；数字"3(sān)"在南方口音下极易转成"山(shān)"。
- **解法**：加"ASR 静默纠偏映射表"，列出同音变体并规定静默等价替换，同时明令禁止纠错用户（不能说"您说的是不是站点3"），直接输出标准导航指令。同法可复用于"元宇宙/原宇宙"、"站点寺/站点4"。

---

## 37. 调工作流时大屏静默或过渡词复读

- **现象**：查航班接口耗时 2-3 秒，大屏无声音像死机；或回复里把"正在为您查询"说了两遍。
- **原因**：原 Prompt 未考虑接口延迟；加了过渡词又没约束出现次数，模型在最终播报时重复前缀。
- **解法**：两阶段延迟补偿——发起查询时只输出一句过渡词并立即调用工作流；拿到结果后直接播报结果，严禁复述过渡词，整轮只允许出现一次。查无结果时给独立兜底话术。

---

## 38. 新增需求与既有红线正面冲突

- **现象**：客户要求在科普后推荐科室并引导扫码，但原 Prompt 有一条"绝对禁止主动反问"的核心体验红线。
- **原因**：把"引导扫码"默认写成了问句（"您需要扫码挂号吗？"），与新需求天然打架。
- **解法**：保红线、改句式。所有引导动作写成陈述句——"建议挂儿童保健科，您可扫描下方二维码预约挂号。以上内容仅供参考。"并在修改说明里点明"100% 遵守不主动反问的红线"。

---

## 39. 只改 Prompt 不改 RAG，二维码弹不出来

- **现象**：Prompt 已写"引导用户扫码"，实际对话中二维码不弹。
- **原因**：二维码由 RAG 召回富媒体卡片触发，知识库文档没有对应切片和图片资产，Prompt 写得再准也调不出来。
- **解法**：同步交付知识库文档规范——按 QA 切片、每片挂同一张图片资产、覆盖全部高频关键词（肥胖/视力/心理/口腔/挂号），并在平台侧把图片配成对应卡片组件。

---

## 40. Prompt 内部数量与序号自相矛盾

- **现象**：列了 4 个站点，下一句写"上述 3 个地点以外"；并列出现两个 `2.`。
- **原因**：客户多轮手工编辑留下的笔误，未被清理。
- **解法**：改版时逐条核对数量描述与序号连续性。数量写错会让白名单校验失准，序号错乱会降低模型对限制条款的执行精度。

---

## 41. 把参考脚本原样抄成 Few-Shot

- **现象**：客户给一段发布会/接待脚本，改版后整段塞进示例，模型开始输出"（播放3D数字人视频）""（递名片）"等舞台提示。
- **原因**：脚本是给人看的演出稿，含舞台提示与硬件切控指令；照抄等于把这些提示教给模型。
- **解法**：先抽出必须复现的交互节奏写成编号步骤（"您讲"→"好的"→知识库解答），脚本原句降级为 Few-Shot；舞台提示、视频播放、硬件动作一律交给后台系统，Prompt 内不出现。

---

## 42. 压平的 Prompt 直接动手改

- **现象**：客户从聊天框粘贴的 Prompt 被压成一行，标题层级、列表、换行全丢，改版时误判章节归属，把红线写进了技能区。
- **原因**：纯文本粘贴丢失 Markdown 结构，`# 角色 你是某科技公司的机器人"小智"，面向 C 端用户……` 整段挤在一起。
- **解法**：先按语义复原 `#`/`##`/`-` 层级，确认每段归属后再动内容。结构没复原就改，等于在一段散字上做手术。
